赛题 14 · 面向智能体的内存管理系统

agent-mem v1 — 技术架构与分层评估方案

在 vllm-ascend / 昇腾 910B 之上，针对智能体推理的独特内存特征，构建一套可独立 toggle、可组合、可复现的内存优化系统，并以 baseline → MVP → ours 三档递进证明每一项工作的必要性。

Ascend 910B2C · 64GB HBM vllm-ascend 0.22.1rc1（CUDA-free） 910B = BF16（无 FP8 → KV 走 int8/C8） 5 功能 F1–F5 · 7 条稳定缝 统一 benchmark（tau-bench + longbench）
⚠️ 数字来源声明：本文指标来自各功能分支的真机实测；v1 统一分支上的 before/after 重跑待 NPU 启用。所有对照遵循"同硬件 / 同模型 / 同 prompt / 同 seed、3 次取中位数"。

1. 我们在解决什么问题

智能体推理 ≠ 普通单轮生成。它的内存使用有 5 个独特特征，每个都是一条独立的优化机会——也是赛题的评分指挥棒。

智能体内存特征（痛点）不优化的后果我们的解
① 系统/工具 prompt 每轮重复prefill 反复算同样前缀，TTFT 高prefix cache（MVP）+ F2 压缩
② 多轮 KV 持续累积，单 session 寿命长HBM 吃紧 → 抢占重算 / OOMF5 动态回收 + F4 分层
③ 工具返回值（HTML/长 JSON）一次性塞进 contextcontext/KV 膨胀F3 lazy-load
④ KV 显存绝对占用大并发上限低、易 OOMF1 C8 量化
⑤ 多 session 并发 + 价值异构（忙/闲不一）抢占误伤活跃 sessionF5 会话感知调度

2. 技术架构：7 条稳定缝 + 5 个独立功能

每个功能挂在一条"稳定缝（seam）"上——有自己的 yaml、自己的开关、走现成 harness 出自己的 before/after，可单独测、可组合。这是整个系统能"独立 toggle 又能叠一起"的地基。

2.2 统一缝C：一个 connector 槽，yaml 二选一

F4（LMCache）与 F5-Phase2（SimpleCPUOffload）原本抢同一个 --kv-transfer-config 槽（vLLM 只接受一个 connector）。v1 把三种不兼容写法收敛成一个 schema：

engine:
  kv_transfer:               # 缝C 唯一槽，后端二选一
    connector: LMCacheAscendConnector      # 或 SimpleCPUOffloadConnector
    role: kv_both
    extra_config: { ... }
  c8: { enabled, patch_qwen2 }             # F1（缝A）
  priority_scheduling: true                # F5（缝A scheduling flag）

已验证：F4 档 → LMCacheAscendConnector，F5-P2 档 → SimpleCPUOffloadConnector，二者经同一个 render_kv_transfer_arg 渲染。F5 核心（准入+优先级）始终叠加在 connector 之上，与 connector 互不冲突。

3.1 为什么 T1 要放"no-op flag"——这是必要性证明，不是凑数

T1 不止 prefix cache，而是"不写代码、只靠启动参数能开的一切"。其中有几个开了等于没开——这恰好证明了我们为什么要写 F1 / F5：

vllm 免费 flag开了之后结论我们的回应
prefix caching（V1 默认）真有用解决特征①（prompt 重复）作为 MVP 基线保留
--kv-cache-dtype int8no-op0.22.1rc1 后端硬断言 scales==1，不路由到 C8F1：c8.py 校准 + Qwen2 patch 才让 int8 KV 真生效
--scheduling-policy priority≈FCFS给所有 session 同优先级时几乎无增益（实测 A≈B）F5：准入控制 + combined priority 才真消除抢占

于是 T1 → T2 的跳变就是"必要性证明"：免费 flag 给不了的东西，必须靠我们的代码。这比单纯的"off vs on"有说服力得多。

3.2 特征消融基线 = T1

每个 F 功能的 before/after 都对照 T1（prefix cache ON + 全 F 关），单变量 toggle。这样既公平（prefix cache 是真实部署默认，不是造虚高），又与三档递进共享同一个中间档——一个定义，两个用途，无术语冲突。F5 尤其依赖此基线：它的 KV 命中提升本质是"保护 prefix cache 不被抢占打掉"，prefix cache OFF 时该指标无意义。

5. 测试场景：尊重每个功能的"触发条件"

一个功能只在它的触发条件满足时才有收益。所以不搞"一套统一场景跑全部"（会系统性低估未触发功能），而是每个功能配最能触发它的场景，单变量对照 T1。5 个触发条件聚类成 2 个场景族：

场景族workload触发谁对照（单变量 toggle vs T1）
α 并发资源受限unified-tau-freq：6 并发 τ-bench + 小 KV pool（--gpu-memory-utilization 0.27）+ think-time profilesF5 / F1 / F4F5: T1→combined-evict+准入 ｜ F1: T1→c8 ｜ F4: T1→LMCache
β 长上下文 / 大工具unified-longbench：LongBench 2WikiMQA（大 context 当工具结果）F2 / F3F3: T1→lazyload ｜ F2: T1→compress
γ 集成（headline）综合 workload（α 压力 + β 长context 同时造）全部T1（全关）→ T2（全开）整体显存/延迟/成功率

共享：同一 harness（统一 benchmark）、同一套 RunMetrics、同模型（Qwen2.5-7B + MiniCPM3 各跑，命中"通用性"）、成功率红线 ≤2pp、3 次中位数。

诚实判读：Layer 1（每功能触发消融）= 各功能"上限/潜力"；Layer 2（γ 集成）= 现实整体效果，可能 < 各功能之和（综合场景未必同时触发所有条件 + connector 二选一等约束）。两者是不同问题，不要把 γ 的"整体只快 X%"当成某功能没用。
