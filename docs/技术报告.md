# 第 1 章　绪论

## 1.1 研究背景

### 1.1.1 大语言模型智能体的推理范式演进

随着大语言模型（Large Language Model, LLM）能力的快速提升，其应用形态已从简单的单轮文本生成逐步演进为以智能体（Agent）为核心的复杂推理范式。在传统单轮推理场景中，用户输入一条提示，模型生成一条回复，整个过程在数秒内完成，推理生命周期短暂且线性。然而，基于 LLM 的智能体系统需要完成规划（Planning）、执行（Action）、反思（Reflection）的多阶段循环过程，其推理生命周期从秒级扩展到分钟级甚至更长。

以典型的 ReAct（Reasoning + Acting）范式为例，智能体在接收到用户任务后，首先进行任务分解与规划，然后根据当前状态选择并调用外部工具（如搜索引擎、数据库查询、API 调用等），获取工具返回结果后评估是否需要进一步操作，如此循环直至任务完成。在这一过程中，智能体与推理引擎之间发生大量的多轮交互，每轮交互都需要将完整的对话历史、系统指令、工具定义和工具返回数据重新送入模型进行下一次推理。

这种范式转变使得推理系统的内存管理面临根本性的挑战。传统推理框架（如 vLLM）主要面向线性序列生成的场景进行优化，其内存管理策略假定请求之间相互独立、生命周期短暂。然而，智能体推理中长生命周期的上下文维护、多轮工具调用的中间数据累积、以及可能的推理路径分支等特性，都对内存管理系统提出了全新的需求。

### 1.1.2 Agent 推理的内存特征与挑战

相较于传统单轮推理，LLM 智能体推理在内存使用上呈现出五个显著不同的特征：

**（1）KV Cache 持续累积。** Transformer 模型在自回归生成过程中，每个 token 的 key 和 value 激活值会被缓存为 KV Cache，以避免后续 token 生成时的重复计算。在单轮推理中，KV Cache 的生命周期与单次请求绑定，请求结束后即释放。然而在智能体多轮对话场景中，同一会话的上下文持续增长，KV Cache 随轮次不断累积，单会话的 KV Cache 寿命远超 single-shot 请求，对显存形成持续压力。

**（2）上下文内容高度冗余。** 智能体推理中，系统提示（system prompt）和工具定义（tool schema）在每个推理轮次中都需要完整发送给模型。以 τ-bench retail 场景为例，首轮完整提示中系统策略约 1,188 token，16 个工具的 schema 约 3,047 token，两项合计占首轮输入的绝大部分，且每轮重复发送。此外，多轮对话中的历史消息包含大量自然语言叙述和工具返回描述，存在显著的信息冗余。

**（3）推理路径可能出现分支。** 在需要复杂推理和决策的场景中，智能体可能采用自洽性（Self-Consistency）或树搜索（Tree-of-Thoughts）等策略，对同一状态生成多个候选推理路径。这些分支路径共享相同的前缀上下文，但各自产生分叉后的独立 KV Cache。若不加以优化，分支推理将导致显存占用的成倍增长。

**（4）工具调用带来大规模中间数据。** 智能体在执行任务时频繁调用外部工具，工具返回的数据（如搜索引擎返回的长文档列表、数据库查询返回的大量订单记录、API 返回的 JSON 结构等）可能包含数千甚至上万个 token。这些中间数据被完整放入对话上下文参与下一轮推理，不仅增加了 KV Cache 的占用，还可能超出模型的上下文窗口限制。

**（5）内存生命周期长，结构动态，复用性要求高。** 智能体推理的内存需求具有高度的动态性：同一会话的不同阶段对上下文的需求不同，不同会话之间的活跃度也存在差异。理想的内存管理系统需要能够根据会话状态动态调整资源分配，在显存紧张时将闲置会话的 KV Cache 换出，在需要时快速恢复，实现高效的资源复用。

上述五个特征使得支撑智能体推理的内存管理系统面临内存生命周期长、结构动态和复用性要求高等核心问题和需求。在资源受限或多任务并发环境下，低效的内存管理策略将显著增加显存占用，导致推理延迟上升甚至任务失败。

### 1.1.3 国产 AI 硬件生态与异构加速

近年来，国产 AI 加速硬件快速发展，以华为昇腾（Ascend）NPU 为代表的国产芯片在算力和生态方面持续进步。华为 Ascend 910B 系列 NPU 采用达芬奇架构，提供 64 GB HBM 显存，通过 CANN（Compute Architecture for Neural Networks）软件栈提供完整的 AI 推理支持。在操作系统层面，openEuler 作为国内主流的开源 Linux 发行版，提供了针对昇腾硬件的容器化部署镜像和配套工具链。

在推理框架方面，vllm-ascend 是 vLLM 官方社区针对昇腾 NPU 的适配插件，以 V1 架构为基础，通过 `torch_npu` 算子库将 vLLM 的推理能力迁移到昇腾平台。vllm-ascend 继承了 vLLM V1 的 PagedAttention 分页管理、自动前缀缓存（Automatic Prefix Caching, APC）、KV connector 框架等核心机制，并针对昇腾硬件特性进行了专门优化。然而，在智能体推理的内存优化方面，vllm-ascend 仍处于起步阶段，大量的优化空间有待探索。

本文作者团队在 Ascend NPU 平台上具有深厚的技术积累。在前期的 GitLink 2026 开源竞赛中，团队成功在 vllm-ascend 上实现了 AWQ、GPTQ、torchao、GGUF 四种 weight-only 量化参数的完整适配，累计贡献约 5,800 行纯 Python 代码和 401 项测试用例，相关成果已向 vllm-ascend 官方仓库提交合并请求。这一前期工作使团队深入掌握了 vllm-ascend 的架构设计、Ascend Scheme 框架、NPU 算子特性以及 CANN 环境的排障经验，为本文面向智能体推理的内存管理优化工作奠定了坚实的技术基础。

## 1.2 国内外研究现状

### 1.2.1 推理引擎与 KV Cache 管理

在 LLM 推理引擎领域，vLLM 是最具影响力的开源项目之一。其核心贡献 PagedAttention 借鉴了操作系统中虚拟内存的分页管理思想，将 KV Cache 的存储从传统的连续张量切分为固定大小的 block，并通过 block table 进行映射管理。这一设计从根本上解决了传统推理框架中 KV Cache 的内存碎片化和整体预分配浪费问题。vLLM V1 架构进一步引入了自动前缀缓存（APC）机制，当多个请求共享相同的前缀文本（如 system prompt）时，对应的 KV block 只存储一份，通过引用计数实现隐式的 Copy-on-Write 共享，显著降低了冗余存储。

llama.cpp 是另一款广泛使用的 LLM 推理框架，以纯 C/C++ 实现和高效率著称。在 KV Cache 管理方面，llama.cpp 支持多种量化格式（如 Q4_0、Q8_0 等），通过将 KV Cache 从 FP16 量化为低精度格式来减少内存占用。此外，llama.cpp 实现了基于 flash attention 的高效注意力计算，利用缓存局部性减少 HBM 访问。

SGLang 提出了 RadixAttention 机制，基于 radix 树结构组织 KV Cache 的共享前缀，在多个请求间实现比 vLLM APC 更灵活的 KV 复用。然而，SGLang 目前不支持 Ascend NPU，其 radix 树实现在昇腾平台上无法运行。在工业界，Mooncake 提出了分布式 KV Cache 池化方案，将 KV Cache 从单卡 HBM 扩展到跨实例的共享存储层。上述工作为 LLM 推理的 KV Cache 管理提供了重要基础，但大多面向通用推理场景设计，缺乏对智能体长生命周期、多轮对话、工具调用等特有模式的针对性优化。

### 1.2.2 上下文压缩技术

针对 LLM 推理中上下文长度持续增长的问题，上下文压缩技术提供了一条有效的优化路径。Microsoft 提出的 LLMLingua 系列方法是该领域的代表性工作。LLMLingua 基于小型语言模型（如 GPT-2、BERT）对长上下文中的每个 token 进行重要性评估，通过困惑度变化量衡量每个 token 对理解上下文的信息贡献，保留高信息密度 token 而丢弃冗余 token。LLMLingua-2 进一步将压缩模型替换为多语言 BERT，在保持压缩效果的同时将推理速度提升 3 至 6 倍，且不依赖 GPU，可在 CPU 上高效运行。Selective Context 采用类似思路，通过计算 token 级别的自信息来评估冗余度进行动态裁剪。此外，AutoGen 等智能体框架也提供了压缩式对话历史管理的集成接口。

然而，现有的上下文压缩方法主要面向通用文本设计，缺乏对 Agent 推理中特殊协议结构的感知。例如，OpenAI 工具调用协议中的 `tool_calls` 结构（包含 call_id、function name、arguments 等关键字段）对任务执行的正确性至关重要，标准压缩算法可能错误地裁剪这些结构化字段，导致工具调用失败。如何在压缩效率与协议正确性之间取得平衡，是面向 Agent 推理的上下文压缩技术需要解决的核心问题。

### 1.2.3 分层存储与异构内存

GPU 显存容量有限且价格昂贵，而 CPU 主存和 SSD 存储具有更大的容量和更低的成本。分层存储方案通过在 GPU 显存、CPU 主存和磁盘之间动态迁移数据，突破单一存储层级的容量限制。

LMCache 是分层 KV Cache 方案的代表性项目，支持 GPU→CPU→Disk 三级分层架构。在 GPU 显存紧张时，LMCache 自动将冷 KV block 卸载到 CPU 内存或磁盘，当请求需要这些 block 时再异步加载回 GPU。LMCache-Ascend 作为社区插件，将 LMCache 适配到 Ascend NPU 平台，使用 `aclrtMemcpyBatchAsync` 和 `torch.npu.Stream` 实现 NPU↔CPU 的高效异步传输。vllm-ascend 官方提供了 SimpleCPUOffloadConnector，支持 lazy 卸载模式：当 KV block 即将被淘汰时自动在 CPU 侧保留副本，后续如有 cache hit 则可从 CPU 便宜恢复。分层存储方案面临的共同挑战在于如何在 GPU 显存中保留足够多的"热"数据以保证推理延迟，同时充分利用 CPU 和磁盘的大容量来容纳"冷"数据。对于智能体推理而言，会话的冷热状态随用户交互动态变化，需要更细粒度的会话感知策略来指导分层调度。

### 1.2.4 工具调用数据优化

智能体在执行任务过程中频繁调用外部工具，工具返回的结构化数据（JSON 数组、HTML 页面、CSV 表格等）往往体量庞大。传统做法将这些数据完整放入对话上下文，直接推高 KV Cache 占用和预填充延迟。

ByteDance 的 DeerFlow 框架提出了 ToolOutputBudgetMiddleware 机制，为每个工具的输出设定 token 预算上限，超限输出被持久化存储并从上下文中移除，模型在需要时通过专门的检索接口按需获取受限数据。该设计确立了"外置存储 + 按需取回"的基本范式，但其检索接口以行分页为主，对结构化数据的字段级定位支持有限。Mem0 和 LangChain 的 retriever 模式则提供了基于引用 ID 的间接访问方式，模型可通过 fetch 调用取回原文，但缺点在于模型无法预先了解数据结构信息，可能盲目调用 fetch 却获取不到所需字段。对于智能体推理而言，理想的工具数据管理方案需要同时满足三个条件：大规模结果从 KV Cache 路径中移除；上下文中的引用标记提供充分的结构摘要信息；取回接口支持结构化定位，避免无效往返。

# 第 2 章　技术理论

## 2.1 KV Cache 与推理引擎基础

### 2.1.1 Transformer 自回归推理中的 KV Cache 原理

Transformer 模型的自回归生成过程本质上是逐 token 的序列预测。给定输入序列 X = [x_1, x_2, ..., x_n]，模型需要依次预测后续 token。在每一生成步 t，模型对当前完整序列计算注意力：

Attention(Q, K, V) = softmax(QK^T / sqrt(d_k)) V

其中 Q（Query）仅需对最新 token 计算，而 K（Key）和 V（Value）需要对所有历史 token 计算。若每次生成都重新计算所有历史 token 的 K 和 V，计算复杂度为 O(n^2)。KV Cache 的核心思想是：将已计算过的历史 token 的 K 和 V 张量缓存于显存中，每次新 token 生成时只需计算最新 token 的 Q、K、V，然后从缓存中读取历史 K、V 进行注意力计算，将每步生成的计算复杂度降为 O(n)。

KV Cache 的显存占用量可通过下式精确计算：M_KV = 2 × L × H × d_h × S × B_dtype，其中 L 为 Transformer 层数，H 为 KV 头数（GQA 场景下 H 远小于注意力头数），d_h 为每头维度，S 为序列长度，B_dtype 为数据类型字节数。以 Qwen2.5-7B 为例（L=28，H=4，d_h=128），当序列长度达到 32,768 时，BF16 格式下 KV Cache 占用约 4.7 GB。在智能体多轮对话中，若单会话累积 100 轮且每轮平均 500 token，则 KV Cache 可达约 7.2 GB，多会话并发时显存压力显著。

### 2.1.2 PagedAttention 分页管理与 Block 级调度

vLLM 提出的 PagedAttention 将 KV Cache 管理从连续张量分配改革为分页式管理。其核心思想借鉴了操作系统的虚拟内存机制：将 KV Cache 切分为固定大小的 block（默认 16 token/block），通过 block table 建立逻辑序列位置到物理 block 地址的映射。这一设计的三层面优势：按需分配 block 消除内部碎片——传统方案需预分配最大序列长度的连续 KV 空间，PagedAttention 实际占用接近序列真实长度；统一 block 粒度消除外部碎片——不存在不同请求间拼接时的大小对齐问题；灵活的 block 级共享——不同请求可共享同一物理 block（如共享 system prompt 的 KV），通过引用计数管理 block 生命周期。

vLLM V1 架构的 block 管理器维护全局 block 池，通过 LRU 策略管理 block 的分配与回收。当显存紧张时，调度器根据优先级选择 victim 请求，释放其占用的 block。

### 2.1.3 自动前缀缓存与隐式 Copy-on-Write

自动前缀缓存（APC）是 vLLM V1 的核心优化机制。其工作原理是：当处理新请求时，引擎对 token 序列按 block 粒度计算哈希值，在全局哈希表中查找是否存在已缓存的匹配 block。若命中，则直接复用该 block 的 KV 数据，免去对应的 prefill 计算。

对于共享同一前缀的请求序列，APC 的复用效果最为显著。在智能体推理中，system prompt 和 tools schema 对所有请求完全相同——这正是 APC 的最佳应用场景。当多个请求共享某前缀 block 时，该 block 的引用计数大于 1。当某个请求需要修改该 block 的内容（即分叉），APC 实现隐式的 Copy-on-Write：为该请求分配新 block 存储分叉后的 KV，而共享前缀的 block 仍被其他请求引用。这种 block 级别的隐式 CoW 无需显式的 fork API，对上层透明，对于分支推理场景天然提供了 KV 复用支持。

## 2.2 KV Cache 量化理论

### 2.2.1 对称 per-channel int8 量化的数学基础

KV Cache 量化的目标是将 BF16/FP16 格式的 Key 和 Value 张量压缩为 int8 格式，使单个 token 的 KV 存储从 2 字节降低为 1 字节。本文采用对称 per-channel 量化方案，其数学定义为：q = round(x / s)，其中 s = max(|x|) / 127，x 为原始浮点值，s 为 scale 因子，q ∈ [-128, 127] 为量化后的 int8 值（对称量化不使用 zero-point）。反量化过程为 x̂ = q × s，量化误差来源于 round 操作的截断。

per-channel 的"channel"指 K/V 头的维度 d_h。对于每个注意力头，沿 d_h 维度逐位置计算独立的 scale，而非整个张量共享一个 scale。这使得量化粒度更细，能够更好地适应不同通道的数值分布差异。以 Qwen2.5-7B 为例（d_h=128，4 个 KV 头），每层共有 4 × 128 = 512 个通道，每个通道有一个独立的 scale。per-channel 量化的往返相对误差 ε = |x̂ - x| / (|x| + ε)，在标准分布假设下预期误差在 0.5% 以内。

### 2.2.2 RoPE 旋转位置编码对 KV 量化的影响分析

旋转位置编码（RoPE）将位置信息通过旋转矩阵嵌入 Q 和 K 向量。对于位置 m 处的向量 x ∈ R^d，RoPE 将其按维度对分组后施加旋转。其中频率参数 θ_i = 10000^{-2i/d}，i = 0, 1, ..., d/2-1。

本文通过实验发现，RoPE 对 KV 量化存在关键影响：vLLM V1 存储到 KV Cache 中的 K 是 post-RoPE（旋转后）的张量，而非 pre-RoPE（旋转前）的 k_proj 输出。RoPE 的旋转操作会显著改变 K 张量的逐通道振幅分布，尤其对早期层影响剧烈。实测数据显示（Qwen3-0.6B，910B2C），第 0 层 post-RoPE K 的逐通道最大绝对值是 pre-RoPE 的 435 倍，第 7 层约为 29 倍，逐层递减，至第 27 层约为 1.2 倍。

这意味着若校准脚本错误地从 k_proj（pre-RoPE）采 scale，早期层的 scale 会比实际需要的小数个数量级，导致量化后大量值饱和截断（第 0 层 68% 的值超过 127），反量化严重错位，最终产生完全不可读的输出。正确的做法是从 post-RoPE 位置采 scale，此时 quant→dequant 的往返误差仅约 0.5%。

### 2.2.3 Ascend C8 静态反量化与图编译模式适配

vLLM-Ascend 的 int8 KV 量化通过 C8（CANN int8）机制实现，其激活路径为：模型目录写入 quant_model_description.json（标记 kv_cache_type: "C8"）+ 引擎启动时添加 --quantization ascend，触发 AscendC8KVCacheAttentionMethod。C8 采用静态 per-channel 反量化方案：scale 从模型权重文件加载（经过 post-RoPE 自校准后注入 safetensors），不依赖运行时动态标定。

C8 将 KV Cache 的注意力计算走 npu_fused_infer_attention_score + int8 分页 KV + per-channel antiquant，KV 数据按 NZ BNSD 布局存储。然而，该 attention 路径在 FULL ACL-graph capture 模式下对大 decode batch 存在确定性死锁——NPU 在 graph capture 阶段空转（NPU 101W 状态），无法完成编译。经过实验排查，死锁根因是 decode 阶段走 FULL graph。解决方案是将编译模式改为 FULL_DECODE_ONLY——prefill 阶段仍走 FULL graph（计算密集，graph 收益大），decode 阶段退化到 eager 模式，绕开死锁路径。由于 decode 阶段的计算模式相对规整（每次仅处理增量 token），eager 执行的开销在 int8 KV 带宽收益的抵消下不再显著。

## 2.3 上下文压缩理论

### 2.3.1 Token 级重要性评估与 LLMLingua-2 压缩算法

LLMLingua-2 是一种基于小型 BERT 模型的 task-agnostic prompt 压缩方法。其核心算法流程为：给定一段文本 T = [t_1, t_2, ..., t_n]，BERT 编码器对每个 token t_i 生成上下文表示 h_i，然后通过一个轻量分类头预测每个 token 的"保留/丢弃"二值决策。训练时使用知识蒸馏：教师模型（大 LLM）在完整文本和压缩文本上的输出分布差异作为监督信号，使学生模型学会在保持 LLM 理解一致性的前提下最大化压缩率。

LLMLingua-2 的推理过程在全 CPU 上完成（不依赖 GPU），单次压缩延迟在 3-6 秒之间（取决于文本长度和 BERT 模型规模），较 LLMLingua 初代的 GPT-2 方案（约 20-26 秒）快 3-6 倍。其使用的 multilingual BERT 模型对中英文混合文本具有良好的跨语言压缩能力。压缩率定义为 R = |T_compressed| / |T_original| × 100%，R 越小压缩越激进。对于 LLM 推理而言，压缩的目标是在 R 和下游任务质量之间找到最佳平衡点。

### 2.3.2 冷热分层与增量压缩的触发策略

LLMLingua-2 虽然比 LLMLingua 初代更快，但每次压缩仍需数秒 CPU 时间。对多轮 Agent 对话而言，历史消息逐步累积，若每轮都对全量历史重新压缩，累计开销将不可忽视。为此本文提出了冷热分层与增量压缩策略：

**冷热切分。** 将当前对话历史分为"热尾"（Hot Tail）和"冷区"（Cold History）。热尾定义为最近 K 条完整消息组（K=6），其中消息组以 assistant tool call 与其对应的 tool result 为不可分割的边界——切分点必须保证不产生孤立的 tool message 违反 OpenAI 协议。热尾直接保留原文，冷区为可压缩对象。

**双阈值触发。** 冷区的可压缩正文累计 token 数达到 trigger_tokens（默认 8,000）时首次触发 BERT 压缩；之后冷区新增可压缩正文每累积 recompress_delta_tokens（默认 4,000）时重新构造冷区进行压缩。在两次压缩之间，后续请求直接复用已压缩的冷区，仅将新增冷消息原样附加。这一设计将压缩次数从"每轮一次"降低到"每 N 轮一次"。

**压缩缓存。** 对相同的（rate, body）组合按 body 的 SHA-256 缓存压缩结果；session 级冻结冷段缓存和进程级 token-count 缓存进一步降低重复开销。实测在 τ-bench retail 全量 115 任务中，复用率达 78%。

### 2.3.3 Agent 协议结构感知的关键字段保护

标准文本压缩算法对 Agent 推理中的特殊协议结构缺乏认知。OpenAI 工具调用协议中，assistant 消息包含 tool_calls 数组，每个元素包含 id（调用标识）、function.name（工具名）和 function.arguments（调用参数）。若压缩错误地裁剪了 call_id 或修改了 arguments 中的 JSON 结构，工具调用将直接失败。

本文提出 tool-aware 结构保护策略，在压缩前对每条消息进行序列化拆分：保护前缀（Protected Prefix）包含 user 消息全文、assistant 的 tool_calls 结构（id/name/arguments）、tool 消息的元数据（call_id/name）以及按 JSON key 白名单匹配到的关键字段值——这些内容物理隔离，100% 不送入压缩器。可压缩正文（Compressible Body）包含 assistant 的自然语言叙述和 tool 结果的描述性文本，按各自的目标保留率（assistant: 75%，tool result: 60%）送入 LLMLingua-2。

关键字段白名单覆盖 Agent 推理中常见的业务敏感字段：ID 类（id、order_id、product_id）、金额类（amount、price、total、balance）、状态类（status、state、reason、confirm）、时间类（time、date）、联系类（email、address、payment），以及 quantity、count、refund、severity、priority、owner、permission 等共 30 余个模式。

## 2.4 工具数据外置理论

### 2.4.1 引用替换模型与确定性结构摘要

当智能体调用的外部工具返回大量数据时，传统方案将这些数据直接放入对话上下文，导致 KV Cache 显著膨胀。本文提出的工具数据外置方案采用引用替换模型：

**外置决策。** 对每次工具返回结果，使用与推理引擎一致的 tokenizer 精确计算 token 数。若结果 token 数 ≥ externalize_trigger_tokens（默认 4,000），则触发外置：原始完整结果存入 session-scoped ArtifactStore，生成唯一不透明 result_id，并构造确定性结构摘要。若结果未达阈值则原样保留。

**确定性摘要。** 摘要的生成完全由 Python 标准库完成，不调用任何额外 LLM，保证确定性和零推理开销。JSON 数据给出根结构、前 12 个 key、最多 4 个 array pointer（含长度和 item key）以及最多 12 个 title；HTML 数据给出 title 和 h1-h3 标题列表；CSV/TSV 给出列名和行数；纯文本给出行数和受限首尾摘录。摘要的目的是让模型了解"数据是什么形状、应从何处取回"。

**上下文替换。** 对话历史中，原始大结果被替换为包含 result_id、结构摘要和 fetch_tool_result 调用提示的轻量引用标记（不超过 512 token）。仅当引用确实比原文短时才执行替换。

### 2.4.2 受限结构化检索的形式化定义

模型在阅读引用标记后，可通过调用本地 fetch_tool_result 工具按需取回数据。该工具提供四类访问模式：（1）RFC 6901 JSON Pointer 定位——按标准 JSON Pointer 语法直接定位到 JSON 中的特定位置。（2）单字段匹配搜索——在 JSON 数组中按字段值搜索匹配记录，匹配模式支持 exact/iexact/contains/icontains，最多返回 10 条。（3）行号分页——以 1-based 行号为索引，每次最多取 100 行。（4）字符偏移继续读取——从指定字符偏移开始读取，单次最多检查 20,000 字符。所有 fetch 响应均受 768-token 硬上限约束。字段搜索不涉及正则表达式、JSONPath 或任意表达式求值，限制于确定性的匹配模式。

### 2.4.3 会话隔离与完整性校验的安全模型

ArtifactStore 实现了严格的会话级安全隔离。会话隔离：每个 artifact 绑定 (session_id, result_id) 联合主键，跨 session 使用相同的 result_id 只会得到 not_found 响应。完整性校验：写入时计算原始内容的 SHA-256 哈希并存储，每次 fetch 前重新计算比对，不一致则拒绝返回。并发安全：SQLite 后端启用 WAL 模式 + synchronous=NORMAL + busy timeout，支持多线程并发读写。TTL 自动清理：每个 artifact 记录创建时间，超时自动删除（默认 TTL = 3,600 秒）。

## 2.5 分层 KV 存储与异步卸载

### 2.5.1 GPU→CPU→Disk 三级存储架构

GPU 显存（HBM）容量有限（Ascend 910B2C 单卡 64 GB，其中模型权重约 14 GB + KV Cache pool 约 41 GB），而 CPU 主存可达数百 GB 且成本显著更低，SSD 存储则近乎无限。分层 KV 存储方案利用这一容量-成本梯度，构建 HBM→CPU→Disk 三级存储体系。第一级 HBM 存放当前活跃请求的"热"KV block，访问延迟最低（约 1 μs 级）但容量最受限。第二级 CPU 主存存放近期可能被复用的"温"KV block，访问需通过 PCIe/NPU 互联总线（约 10 μs 级延迟）。第三级 Disk/SSD 存放长期不活跃的"冷"KV block，访问需经过文件 I/O 栈（约 100 μs - ms 级延迟）但容量近乎无限。数据迁移决策的核心依据是 KV block 的热度——最近访问时间和访问频率。对于智能体推理，同一会话的 KV 应在连续轮次中保持在 HBM，而长时间无交互的闲置会话的 KV 可被迁移到 CPU 甚至 Disk。

### 2.5.2 LMCache 的 KV block 生命周期与淘汰策略

LMCache 是实现三层 KV 分层存储的代表性开源方案，通过 KVConnectorFactory 注册为 vLLM V1 的 KV connector。存储阶段：每个 KV block 从 HBM 写入时根据配置决定是否保留 CPU/Disk 副本。在 lazy_offload 模式下，block 在即将被 LRU 淘汰时异步复制到 CPU，避免了不必要的传输开销。查找阶段：新请求到来时，LMCache 首先在 HBM 中查找匹配 block；未命中则在 CPU 存储层中查找；仍未命中则在 Disk 中查找。任何一层的命中都能避免昂贵的 prefill 重计算。恢复阶段：命中的 block 从 CPU/Disk 异步加载回 HBM，由于 PCIe 带宽远高于 prefill 计算等效带宽，从 CPU 回读 KV 的开销显著低于全量重算。

LMCache-Ascend 是 LMCache 针对 Ascend NPU 的社区插件，使用 aclrtMemcpyBatchAsync（Ascend 的异步内存拷贝 API）和 torch.npu.Stream 实现 NPU↔CPU 的高效数据传输。vllm-ascend 在启动时自动将上游 SimpleCPUOffloadConnector 中的 CUDA worker 替换为 NPU worker（处理 Ascend 的 K/V 分离存储 + 2 MiB 内存对齐）。

### 2.5.3 无损 KV 卸载的异步传输模型

SimpleCPUOffloadConnector 是 vllm-ascend 自带的 CPU 卸载方案，仅覆盖 HBM↔CPU 两级。卸载时，vLLM 调度器决定淘汰某 KV block 后，connector 在释放前通过 aclrtMemcpyBatchAsync 将 block 异步拷贝到预先分配的 CPU pinned memory 中，拷贝操作放入独立的 torch.npu.Stream 不阻塞 NPU 计算流。恢复时，后续请求需要该 block 时检查 CPU 副本是否存在，若存在通过异步 memcpy 从 CPU 加载回 NPU 的 KV pool。

成本分析：在 Ascend 910B2C 上，单 block（16 token × 4 KV heads × 128 dim × 28 layers × 2 bytes ≈ 460 KB per block in BF16）的 PCIe 传输延迟约为 10-20 μs。相比之下，该 block 的 prefill 重算需要完整的 attention 计算（前向通过 28 层 Transformer），即使经过算子优化，重算延迟也在数十毫秒量级。因此 CPU 回读的成本约重算成本的 1/1000，卸载→恢复的端到端收益显著。

## 2.6 会话感知调度理论

### 2.6.1 优先级抢占调度的数学描述

vLLM V1 支持 --scheduling-policy priority，该模式下调度器使用 PriorityRequestQueue 管理请求队列。当 HBM 中 KV pool 利用率达到饱和时，调度器触发抢占：按请求的 priority 值排序，priority 数值越大的请求越先被踢出。被抢占请求的 KV Cache 全部清零（V1 默认 recompute 模式），后续需要时从头重新计算。如果没有应用层干预，所有请求的默认 priority 相同（通常为 0），此时抢占顺序退化为 LIFO 或随机——即"机制正确但策略盲"。

### 2.6.2 HBM 驱动的准入控制与滞回策略

为弥补 vLLM 原生调度的策略盲区，本文设计了应用层准入控制器。其核心决策基于实时 HBM 利用率的双阈值滞回控制：当 HBM 利用率小于 target_lo（70%）时准入新请求；当大于 target_hi（85%）时拒绝准入并驱逐最空闲 session；在滞回区（70%-85%）内保持当前状态不变。滞回区的意义是避免 HBM 利用率在阈值附近频繁波动导致的准入震荡。拒绝准入时，准入控制器选出 idle_seconds 最大的会话，将其 priority 设为 100，借助 vLLM priority 抢占将其踢出，释放的 KV block 被回收进全局池供活跃 session 使用。

### 2.6.3 会话空闲度与资源回收的形式化定义

会话空闲时间定义为 T_idle(s) = t_now - t_last_active(s)，其中 t_last_active(s) 为 session s 最近一次与模型交互的时间戳。回收命中率（Eviction-Hit-Idle Rate）定义为 R_hit = evictions_hitting_idle / total_evictions，其中"命中 idle"指被驱逐的 session 的 T_idle 超过了预设的 idle 阈值（默认 30 秒）。R_hit = 100% 意味着每次驱逐都精准命中真正闲置的 session，没有误伤活跃 session。本文 F5 实验 C 组在 3 次独立 run 中均达到 100%。Session 的 priority 值按空闲度动态计算：p(s) = 100（可被淘汰）if T_idle(s) > idle_threshold，否则 p(s) = 0（受保护）。

## 2.7 多路径决策与分支推理

### 2.7.1 蒙特卡洛树搜索的基本框架

蒙特卡洛树搜索（MCTS）是一种基于随机模拟的启发式搜索算法。本文将其应用于 LLM 智能体的多路径推理实验，采用标准的四阶段循环：

**（1）选择（Selection）。** 从根节点出发沿树向下递归选择子节点直至可扩展的叶子节点。选择策略使用 UCT 公式：UCT(n) = v(n)/n_visits(n) + c × sqrt(ln N_parent / n_visits(n))，其中 v(n) 为节点累积价值，n_visits(n) 为访问次数，c=1.4 为探索-利用权衡系数。第一项鼓励利用已知高价值路径，第二项鼓励探索访问较少的节点。

**（2）扩展（Expansion）。** LLM 对当前状态提出 N 个候选动作（如 Search、Lookup、Finish）。每个动作创建一个新的子节点，节点包含动作文本和执行该动作后的环境观测。

**（3）模拟（Rollout）。** 从新扩展节点出发进行确定性快速模拟（temperature=0，最大 2 步）。LLM 选择每步的第一个候选动作，直至达到终止状态或模拟深度上限。模拟结束时的奖励值作为该路径的估值。

**（4）回传（Backpropagation）。** 将模拟得到的奖励值沿选择路径向上传播，更新每个节点的 v(n) 和 n_visits(n)。搜索结束后扫描全树所有 Finish 节点，按奖励降序取最优答案。

### 2.7.2 前缀共享在分支推理中的 KV 复用潜力

MCTS 扩展阶段产生的多个候选动作对应着从同一父状态出发的多条推理分支。这些分支天然共享从根节点到当前节点的完整前缀。在 vLLM V1 的 APC 机制下，前缀部分的 KV block 被多个分支共享（引用计数 > 1），仅分支后的差异化 token 序列各占独立的 KV block。总 KV 占用量为 M_total = M_prefix + N × M_diff，其中 M_prefix 为共享前缀大小（被 N 条分支复用），M_diff 为单条分支的差异化 KV。

本文在 HotpotQA 多跳问答数据集上通过 MCTS 实验测量了不同分支数下的 KV Cache 命中率变化。实验设置 A 组（无 prefix cache，N=2）、B 组（prefix cache 开启，N=1）、C1-C3 组（prefix cache 开启，N=2/4/8）。结果显示 KV 命中率随分支数提升而逐步上升（从 B 组的 73.3% 到 C3 组的 80.0%），证明了 APC 的隐式 CoW 对分支推理场景的 KV 复用存在正向收益。本节的定位是对分支 KV 共享机制的理论分析和初步探索性测量，完整定量分析留待未来工作。


# 第 3 章　项目介绍

## 3.1 系统总体架构

### 3.1.1 四层架构设计

本系统采用四层架构，自底向上依次为：国产化部署层、推理引擎层、Agent 推理层和 Benchmark 评测层。各层之间通过稳定接口交互，层内组件可独立替换和升级。

**第一层：国产化部署层。** 基于 openEuler 24.03 操作系统和华为 Ascend 910B2C NPU，通过 CANN 9.0.0 软件栈和 torch_npu 2.10.0 提供 AI 算力。vllm-ascend 0.22.1rc1 以 editable 模式安装，作为推理引擎的 Ascend NPU 适配插件。容器化部署基于 openEuler CANN 镜像，以 Docker compose 编排完整服务栈。

**第二层：推理引擎层。** vLLM V1 架构作为推理内核，默认启用自动前缀缓存。引擎层通过 OpenAI-compatible API（/v1/chat/completions 和 /v1/completions）向上层提供统一的推理服务接口。引擎层同时提供 Prometheus 风格的 /metrics 端点，暴露 KV cache 命中率、TTFT、TPOT、E2E 延迟等运行时指标。本层的优化通过三条缝实现：缝A（引擎 flag 预设，如 --quantization ascend 激活 C8 int8 KV 量化）、缝B（引擎后端切换，如 vllm vs vllm-ascend）、缝C（KV connector 配置，如 LMCacheAscendConnector 或 SimpleCPUOffloadConnector）。

**第三层：Agent 推理层。** 自写 ReAct 循环实现多轮工具调用的完整流程。该层的核心扩展点是缝D（上下文中间件），通过有序 MiddlewareStack 在每次模型请求前后、工具结果返回后插入变换逻辑。F2（上下文压缩）和 F3（工具数据外置）均作为缝D 上的独立中间件实现，各自封装为独立类并通过注册表按需激活。

**第四层：Benchmark 评测层。** 基于 Runner Protocol 的可插拔评测框架，支持 τ-bench（零售/航空多轮工具调用）和 LongBench（多跳问答）两类标准化 Benchmark。该层负责实验组配置、指标采集、对照比较和门槛判定，并通过缝E（Session 生命周期策略）接入 F5 的并发调度能力。

### 3.1.2 稳定缝与独立功能模块的设计方法

本系统在设计上遵循"稳定缝 + 独立功能"的模块化方法。稳定缝指系统中存在的一个稳定接口位置——位于同一缝上的功能模块共享接口约束但彼此独立。系统定义了七条稳定缝：

| 缝 | 名称 | 接口形式 | 归属功能 |
|---|---|---|---|
| A | 引擎 flag 预设 | EngineConfig.extra_args（vllm serve CLI 参数） | F1（C8 int8 KV） |
| B | 引擎后端 | EngineConfig.backend ∈ {vllm, vllm-ascend} | F8（多硬件对照） |
| C | KV connector | --kv-transfer-config JSON + connector 注册 | F4（LMCache）、F5-Phase2（offload） |
| D | 上下文中间件 | Middleware.transform_messages() / .intercept_tool_result() | F2（压缩）、F3（lazy-load） |
| E | Session 生命周期策略 | 策略模块挂载于 SessionManager | F5（idle eviction）、F6（checkpoint） |
| F | 自带工作流/demo | Runner Protocol | F7（MCTS/分支测量） |
| G | 部署 | Dockerfile + compose service | F9（国产 OS 部署） |

不同缝的功能天然独立——如 F1 在缝A 改 flag，F3 在缝D 改 messages，互不干涉。同缝内的功能通过独立 yaml 配置隔离——如 F2 和 F3 同在缝D，但 middleware.active: [compress] 和 middleware.active: [lazyload] 可独立开关。

**功能独立性判定标准。** 每个功能被认定为"独立"，须满足全部五个条件：拥有独立的 yaml 预设仅控制自身开关；无前置模块依赖；可走现有 Benchmark harness 出独立的 before/after 对照数据；单元测试可独立运行；可与其他功能组合使用但其价值证明不依赖其他功能。

## 3.2 MVP 基座实现

MVP 基座在本文各功能模块开发之前即已完成，提供了可运行、可评测、可扩展的系统骨架。所有功能模块均以"填空壳"方式接入 MVP 的对应缝位置。

### 3.2.1 Agent 推理循环

Agent 推理循环（agent/react.py）实现了标准的 ReAct 范式。核心函数 run_react() 接收用户任务描述和工具集，在主循环中执行：（1）上下文构造——将 system prompt、tools schema 和对话历史拼接为 OpenAI-compatible messages 格式，通过中间件栈的 transform_request() 钩子进行变换。（2）模型调用——使用 OpenAI Python SDK 调用本地 vLLM 引擎，开启流式传输同步测量 TTFT。（3）响应解析——若返回文本消息则作为最终回复，若返回 tool_calls 则提取 function.name 和 function.arguments。（4）工具执行——调用对应的业务工具函数，获取返回结果，通过 intercept_tool_result() 钩子变换（F3 可能触发外置）。（5）历史更新——将 assistant 消息和 tool 结果消息追加到对话历史，进入下一轮循环直至达到 max_steps 或模型给出最终回复。流式推理模块 stream_chat_with_ttft() 在消费第一个 chunk 时记录 TTFT，在流结束时统计总 token 数和端到端延迟。

### 3.2.2 Benchmark 评测框架

Benchmark 评测框架（bench/）的核心设计是 Runner Protocol——所有 Benchmark 运行器遵循统一接口（run_task() → TaskRunResult），使不同 Benchmark 套件可复用同一套指标采集、对照比较和门槛判定逻辑。SuiteAdapter 抽象层封装 τ-bench 环境的初始化和 reward 判定，支持本地模型和外部 MIMO API 两种用户模拟器；将 LongBench 的 2WikiMultihopQA 改造为多轮工具检索 Agent 场景。bench/compare.py 支持 baseline → optimized 的自动化对照分析，计算六项核心指标的相对变化率并与预设门槛比较——显存峰值降幅 ≥ 30%、延迟改善 ≥ 20%、成功率差 ≤ 2 个百分点，不达标项标红并生成结构化对照报告。六项核心指标包括 e2e_latency_p50_ms/p95_ms、qps、mem_peak_mb、kv_cache_hit_rate、task_success_rate、ttft_ms。

### 3.2.3 推理引擎封装

推理引擎封装模块（server/vllm_server.py）管理 vLLM API server 的完整生命周期。build_serve_args() 将内部 AppConfig 翻译为 vLLM CLI 参数——包括模型路径、端口、gpu_memory_utilization、max_model_len、max_num_seqs 等基础参数，以及 --quantization ascend（F1）、--scheduling-policy priority（F5）、--kv-transfer-config JSON（F4/F5-Phase2）、--compilation-config（C8 graph 模式）等优化参数。start_engine() 以子进程方式启动 vLLM API server，随后进入 /health 端点轮询等待（超时 600 秒）。stop_engine() 通过进程组确保引擎子进程及其后代被完整终止，避免 NPU 资源泄漏。server/stub_openai.py 是一个标准库实现的假 OpenAI-compatible server，在无 NPU 环境下完全模拟 vLLM 的端点，支持工具调用协议和可注入的延迟/失败模拟，使 Agent 层和中间件层的开发和单元测试可完全脱离 NPU 硬件。

### 3.2.4 中间件栈

中间件栈（middleware/base.py）是缝D 的核心基础设施。Middleware Protocol 定义了七个标准钩子：prepare（Benchmark 计时前预热）、transform_request（每次模型请求前，F2 变换 messages/tools、F3 注入 fetch schema）、intercept_tool_result（工具结果返回后，F3 大结果外置为引用）、handle_internal_tool_call（模型发出内部工具调用时，F3 本地执行 fetch）、measurement_baseline（严格配对计量时恢复原始内容）、after_model_call（模型返回 usage 后记录真实 prompt token 日志）、transform_tools（初始化时 F3 注入 fetch schema）。MiddlewareStack 按 middleware.active 列表顺序将多个中间件串联为有序链，每个中间件维护 per-session 的 MiddlewareContext 暂存状态支持并发多 session 数据隔离。

### 3.2.5 配置与复现系统

配置系统（config.py）基于 Python dataclass 实现零外部依赖的 schema 定义与校验。AppConfig 为顶层配置类，嵌套 EngineConfig、BenchmarkConfig、MiddlewareConfig、SessionConfig、C8Config、KVTransferConfig、UserSimConfig 等子配置，所有枚举值通过白名单校验。复现系统（repro.py）为每次 Benchmark 运行创建标准化的 run 目录（logs/<YYYYMMDD-HHMMSS>_<engine>_<model>_<config>_run<N>/），自动记录 config.yaml 复本、git commit hash、pip freeze 环境快照、NPU 硬件信息。系统提供 20 个 yaml 配置预设（configs/），覆盖 baseline、prefix_cache、optimized 三档以及 F1-F5 各功能的独立配置。

## 3.3 KV Cache 量化模块（F1）

F1 模块的目标是将 KV Cache 从 BF16 格式量化为 int8 格式（Ascend 上称为 C8），使相同显存预算下 KV token 容量翻倍。F1 属于缝A（引擎 flag 预设），仅通过修改 vLLM CLI 参数和模型目录元数据实现。

### 3.3.1 C8 注入工具链设计

C8 的激活需要两步操作：（1）模型目录写入 quant_model_description.json，声明 kv_cache_type: "C8" 并为每层标记 k/v_proj.kv_cache_scale 路径；（2）引擎启动时添加 --quantization ascend。这两个操作由 agent_mem/kv/c8.py 提供的纯函数 CLI 工具链完成：annotate_model() 扫描模型权重文件中的 K/V 投影层构造符合 vllm-ascend 规范的 JSON 并写入模型目录；inject_placeholder_scales() 注入占位 per-channel scale（仅探针用途）；restore_model() 删除 C8 产物还原 stock 模型；is_annotated() 检查模型是否已被 C8 标注。工具链设计原则是"纯函数、可测试、无需 NPU"——在 CPU 环境下通过单元测试完全验证（fake model 仅需 config.json + model.safetensors.index.json）。

### 3.3.2 post-RoPE 自校准流程

如 2.2.2 节所述，KV Cache 存储的是 post-RoPE 的 K 张量，因此校准必须从 post-RoPE 位置采 scale。自校准流程（scripts/calibrate_c8_qwen2.py）：（1）加载目标模型到 NPU，注册 v_proj 钩子直采 V 的逐通道 maxabs，monkeypatch apply_rotary_pos_emb 在旋转后捕获 K 的逐通道 maxabs。（2）运行 32 条校准样本收集每层每通道的 maxabs 统计量。（3）计算 per-channel scale s = max(|x|) / 127，钳制最小值 1e-8。（4）将 scale 注入模型 safetensors 文件并更新分片索引。

对于 Qwen2.5-7B 的 Qwen2 架构，vllm-ascend 的 patch_gqa_c8.py 不覆盖 Qwen2（仅覆盖 Qwen3/Glm4Moe/MiniMaxM2），因此额外需要 c8patch/sitecustomize.py——利用 Python 的 sitecustomize 机制在每个解释器启动时（含 vLLM EngineCore 子进程）自动 monkeypatch Qwen2ForCausalLM.load_weights，使 C8 scale 能被正确加载。该补丁通过环境变量 QWEN2_C8_PATCH=1 门控。

### 3.3.3 引擎配置与激活路径

F1 的完整激活路径由 f1-bench-c8.yaml 配置预设驱动。build_serve_args() 读取 c8.enabled → 自动注入 --quantization ascend；读取 c8.patch_qwen2 → 在子进程环境中设置 QWEN2_C8_PATCH=1 + PYTHONPATH 包含 c8patch/；读取 engine.compilation_config → 注入 --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'。还原步骤对称设计：restore_model 删除 quant_model_description.json + kv_cache_scales.safetensors，从 .stock.bak 恢复原始分片索引。

## 3.4 上下文压缩模块（F2）

F2 模块的目标是对 Agent 推理中每轮重复的 system prompt 和累积的对话历史进行压缩，降低 Prompt token 占用。F2 属于缝D（上下文中间件），通过 CompressMiddleware 实现。

### 3.4.1 静态精简与工具描述去重

**System prompt 精简。** τ-bench retail 的原始 system policy 约 1,188 token。F2 提供了人工审计的 COMPACT_RETAIL_POLICY 精简版，保留核心行为约束（认证、单用户、显式确认、订单状态管理、退款/退换货规则、一次性调用限制等），将 policy 压缩至约 445 token（节省 63%）。对于非 retail 场景，compile_policy.py 工具支持离线编译通用 policy artifact——使用 MIMO 大模型对原始 policy 进行结构化精简，输出包含 source unit 列表和 SHA-256 校验和的 JSON artifact。运行时进行三重确定性校验：source hash 一致性、数字/ID/引号字面量不变、模态短语逐条验证。校验失败自动回退到原始 system prompt。

**工具描述去重。** 对 tools schema 中的所有 description 字段进行扫描，重复内容被提取为 C1/C2/... 共享约定在 system prompt 中出现一次，原工具描述中替换为 See Cn. 引用。工具的 name、type、required、enum 和参数结构保持不变，确保 OpenAI tool-call 协议完整性。

### 3.4.2 动态压缩的冷热分层与 worker 池

CompressMiddleware 实现了动态历史的冷热分层压缩。

**冷热切分算法。** 以最近 keep_hot=6 条消息为 hot tail，其余为 cold history。切分边界向前移动直到 assistant tool_call 与其 role=tool 结果构成完整消息组——确保 OpenAI tool-call 协议中不出现孤立的 tool message。

**双阈值触发与增量复用。** 冷区可压缩正文的 Qwen tokenizer 精确计数达到 trigger_tokens=8000 时首次触发压缩，压缩后 cold 段被冻结，后续请求直接复用。新增 cold 消息每累积 recompress_delta_tokens=4000 时重新压缩。在冻结期内新 cold 消息原样附加。这一设计将压缩次数从 O(N) 降为 O(N/Δ)。

**隔离 worker 池。** 压缩任务在独立 Python 子进程中执行（.venv-compress，transformers 4.43.4），通过 JSONL stdin/stdout RPC 与主进程通信。_SubprocessCompressorPool 维护 N 个常驻 worker（默认 4），支持任务级并行压缩。worker_threads=0 时自动设为 CPU 核数/pool_size。worker 内 LLMLingua-2 BERT 模型懒加载一次跨请求复用。

**三级缓存。** session 级冻结 cold 段缓存；(rate, SHA-256(body)) 压缩结果缓存跨 session 复用；4,096 项 token-count 缓存。缓存命中时压缩延迟从约 7 秒降至约 6 毫秒。

### 3.4.3 通用策略编译与校验

benchmarks/compile_policy.py 是通用 policy 的离线编译工具。输入 Markdown 格式的原始 policy 文件，使用 MIMO 大模型进行结构化精简，输出包含 source unit 列表和 SHA-256 校验和的 JSON artifact。artifact 加载时进行逐 unit 的字面量、数字和模态词校验。若 source hash 不匹配或任何 unit 的强制保留词缺失，默认模式回退到原始 system prompt，确保"宁可不用压缩，不可用错压缩"的原则。

## 3.5 工具数据外置模块（F3）

F3 模块的目标是将大规模工具返回结果从对话上下文中移除（存入外部 store），在 Agent 历史中仅保留轻量引用标记，模型通过本地 fetch_tool_result 工具按需取回。F3 属于缝D，通过 LazyLoadMiddleware 实现。

### 3.5.1 ArtifactStore 的存储后端设计

ArtifactStore 定义了统一的持久化协议：store(session_id, tool_name, content) → result_id，fetch(session_id, result_id) → Artifact | None，delete()，sweep_expired(ttl_seconds)。两种后端实现：MemoryArtifactStore（Python dict + threading.Lock，线程安全但易失，主要用于单元测试和调试场景）和 SQLiteArtifactStore（持久化后端，(session_id, result_id) 联合主键，写入时自动计算 SHA-256 并读取时交叉校验，启用 WAL 模式 + synchronous=NORMAL + busy timeout 5s，TTL sweep 定期清理过期 artifact）。

### 3.5.2 确定性摘要与受限检索接口

**外置决策流程。** LazyLoadMiddleware.intercept_tool_result() 在工具结果返回后立即执行：exempt tool 或 per-tool override 阈值 ≤ 0 → 原样通过；使用 Qwen tokenizer 精确计算结果 token 数；< 4000 token → 原样进入对话历史；≥ 4000 token → 执行外置。外置成功后仅当引用确实比原文短且不超过 512 token 时才执行替换。若失败按 on_store_error 策略处理（passthrough/head_tail/raise）。

**确定性摘要（tool_synopsis.py）。** JSON 数据提取根 shape、前 12 个 key、最多 4 个 array pointer、最多 12 个 title；HTML 提取标题和 h1-h3 列表；CSV/TSV 提取列名和行数；纯文本提取行数和受限首尾摘录。超过 5 MB 的数据标记为 oversized。摘要全部由 Python 标准库完成，不调用任何 LLM。

**fetch_tool_result 内部工具。** 支持四类访问模式：RFC 6901 JSON Pointer 定位；单字段匹配搜索（match_field + match_value + match_mode ∈ {exact, iexact, contains, icontains}，最多返回 10 条含稳定 match_pointers）；1-based 行号分页（最多 100 行含 next_start_line）；字符偏移继续读取（单次最多检查 20,000 字符）。所有 fetch 响应受 768-token 硬上限约束。工具调用不经过 τ-bench 环境（handle_internal_tool_call 直接在中间件栈内部处理），确保 fetch 不会错误修改业务状态。

### 3.5.3 F2+F3 组合契约与防循环规则

组合使用时遵循严格的顺序和分层契约。激活顺序为 middleware.active: [lazyload, compress]——F3 必须先于 F2 执行以获取原始完整工具结果。分层阈值：< 1000 token inline 保留；1000-3999 token 由 F2 hot tool-aware 压缩；≥ 4000 token 由 F3 先外置。防循环规则：fetch_tool_result 被同时加入 F3 的 exempt 工具列表和 F2 的 hot tool gate 豁免，确保"fetch 结果再次触发外置"和"fetch 结果触发压缩"都不会发生。

## 3.6 分层存储模块（F4）

F4 模块的目标是通过 LMCache-Ascend 实现 GPU（NPU）→CPU→Disk 三级 KV Cache 分层存储。F4 属于缝C（KV connector），通过配置 KV transfer connector 实现。

### 3.6.1 LMCache-Ascend 的集成与配置

LMCache-Ascend 是 LMCache 社区针对 Ascend NPU 发布的插件，其核心组件 LMCacheAscendConnector 已在 vllm-ascend 0.22.1rc1 的 KVConnectorFactory 中注册。环境适配方面，Ascend 910B2C 需设置 SOC_VERSION=Ascend910B2C 环境变量才能正确编译 NPU 算子；当前环境的 lmcache 0.5.1 为 CUDA 版需降级为 0.4.4 并以 NO_CUDA_EXT=1 禁用 CUDA 扩展编译；agent_mem/kv/lmcache_check.py 提供运行时可用性探测。配置封装方面，f4-lmcache.yaml 将 LMCache 参数封装为声明式配置，build_serve_args() 自动翻译为 --kv-transfer-config CLI 参数。降级兜底：若 lmcache_ascend 包无法安装，备选方案是 kv_offload.yaml。

### 3.6.2 KV connector 注册与引擎接入

vllm-ascend 的 KV connector 框架在引擎启动时通过插件机制自动加载所有已注册的 connector。LMCacheAscendConnector 的加载路径为：vllm-ascend __init__.py → 注册到 KVConnectorFactory → 引擎解析 --kv-transfer-config JSON → resolve_connector() 实例化 → connector 在 scheduler 的 block 生命周期回调中被调用。介入时机包括 block 分配时检查 CPU/Disk 副本并尝试恢复、block 释放时 lazy_offload 模式下在 LRU 淘汰前异步拷贝到 CPU、以及请求完成时按配置决定是否持久化到 Disk。LMCache 对上层 Agent 和推理代码完全透明。

## 3.7 会话感知调度模块（F5）

F5 模块的目标是解决多 Agent session 并发时 KV pool 竞争导致的随机抢占和缓存失效问题。F5 属于缝E（Session 生命周期策略），Phase 1 为有损回收（priority 抢占），Phase 2 叠加无损卸载（SimpleCPUOffloadConnector）。

### 3.7.1 Session 状态机与会话管理器

Session 数据类定义了会话的四态状态机：ACTIVE（正常运行中）→ OFFLOADED（KV 已卸载到 CPU）→ CHECKPOINTED（KV 已持久化到磁盘）→ EVICTED（KV 已完全释放仅保留元数据）。状态迁移由策略模块驱动，遵循 ACTIVE → OFFLOADED → EVICTED 的降级方向，恢复时反向加载。SessionManager 是线程安全的会话注册中心（threading.RLock），核心操作包括 register()、mark_active()、idle_seconds()、sweep()。

### 3.7.2 准入控制器与滞回策略实现

AdmissionController 实现了 2.6.2 节所述的滞回准入控制。should_admit() 方法读取当前 HBM 利用率（通过可注入的 MemBackend 接口，实测时走 NpuSmiBackend 解析 npu-smi info，测试时走 FakeBackend 注入虚拟值），按 target_lo=70% / target_hi=85% 双阈值决策。拒绝准入时选出 idle_seconds 最大的会话，通过驱逐回调将其 priority 设为 100 触发 vLLM priority 抢占。MemBackend 接口已有三种实现：TorchNpuBackend（torch.npu.memory_stats）、NpuSmiBackend（npu-smi info 子进程解析）、FakeBackend（测试注入），使准入控制器可在无 NPU 环境下用 fake 数据进行完整单元测试。

### 3.7.3 优先级驱逐策略与回调注入

PriorityEvictionStrategy 实现了 2.6.3 节所述的优先级映射：idle 超阈值 session → priority=100（可被淘汰），active session → priority=0（受保护）。策略提供两个回调接口供 ConcurrentSessionDriver 注入每个 Agent 任务：priority_fn(session_id) → int 在每轮 LLM 请求前调用，通过 extra_body 字段透传至 vLLM 引擎；on_turn_start(session_id) 在每轮开始时更新会话活跃时间戳。EvictionTracker 线程安全地记录驱逐总次数、命中 idle session 次数和 idle_hit_rate，最终汇入 run summary sidecar 用于 before/after 分析。

### 3.7.4 无损 KV 卸载的叠加架构

F5 Phase 2 在准入控制之上叠加 SimpleCPUOffloadConnector（缝C），实现"准入控制消除抢占 + offload 降低 GPU KV 利用率"的协同效应。配置由 f5-evict-dynamic-offload.yaml 管理。agent_mem/kv/connector.py 的 KVConnectorConfig 负责将声明式配置翻译为 vLLM V1 的 flat JSON schema，修正了 3 个关键 bug：connector 名从已废弃的 pykvconnector 修正为 SimpleCPUOffloadConnector；去除了不被 vLLM 0.22.1 CLI 接受的 --kv-connector flag；JSON 格式改为 V1 flat schema。

## 3.9 多路径决策实验系统

多路径决策实验系统构建了基于 MCTS 的 LLM 分支推理实验环境，用于定量测量 vLLM APC 在不同分支数下的 KV 复用效果。该系统定位为对分支 KV 共享的探索性测量工具，而非本文已完成的优化模块。

### 3.9.1 离线 HotpotQA 环境与 TF-IDF 检索

OfflineHotpotEnv 是一个 gym 风格的离线强化学习环境，使用 HotpotQA distractor 数据集（90,447 训练集 / 7,405 验证集）。环境提供三个动作：Search[query]（TF-IDF 余弦相似度检索，IDF = log((N+1)/(df+1)) + 1，TF = 1 + log(count)）、Lookup[keyword]（精确不区分大小写子串匹配，回退到 TF-IDF）、Finish[answer]（提交最终答案触发判分）。答案匹配采用四级宽松策略：精确匹配 → 子串匹配 → token-F1 ≥ 0.7 → 归一化子串匹配。

### 3.9.2 MCTS v3 搜索框架实现

mcts_search() 实现了 2.7.1 节所述的四阶段 MCTS 循环。v3 版本三个关键改进：（1）Finish 不截断——_parse_actions() 对 Finish 动作的内容不做任何截断，确保答案完整性。（2）确定性 rollout——temperature=0，每步选 LLM 的第一个候选动作，最大 2 步，消除随机方差。（3）全树答案提取——_extract_best_answer() 扫描全树所有 Finish 节点按奖励和模拟值排序取全局最优，避免 v1 中"正确 Finish 在非叶节点被忽略"的问题。

### 3.9.3 实验组配置与数据采集

实验设置五组对照：A 组（无 prefix cache，N=2）、B 组（prefix cache 开启，N=1）、C1 组（N=2）、C2 组（N=4）、C3 组（N=8）。固定参数 max_iters=8，rollout_depth=2，UCT c=1.4。数据采集由统一框架完成：MemSampler 以 2 秒间隔后台轮询 NPU HBM；fetch_vllm_metrics() 解析 /metrics 端点；analyze_mcts_tree() 提取树节点数、最大深度、分支分布。所有数据支持断点续跑（baseline_checkpoint.json），单任务异常隔离。

### 4.1.4 对照实验方法

所有功能模块遵循统一的对照实验规范：同一硬件、同一模型、同一 prompt、同一 seed，仅改变待测功能模块的配置开关。每组配置独立运行 runs=3 次取中位数，避免单次运行的随机波动。对照报告由 bench/compare.py 自动生成，计算各指标相对变化率并与预设门槛比较：显存峰值降幅 ≥ 30%、端到端延迟改善 ≥ 20%、成功率差 ≤ 2 个百分点。不达标项标红，达标项标绿。

对于 τ-bench 实验，用户模拟器的选择对成功率影响显著。本地 7B 模型作为 user-sim 时轨迹短且随机（多数任务 2-7 步即结束，成功率接近零），不能有效反映 Agent 真实能力。正式评测使用外部 MIMO API（mimo-v2.5-pro）作为 user-sim，轨迹长度恢复至 15-20 步，成功率达到可测量水平。对于 LongBench 2Wiki 实验，Agent 环境的 user-sim 被移除（该任务不涉及用户交互），模型直接与检索工具交互完成多跳取证。

## 4.2 F1 C8 int8 KV 量化实验

F1 实验的目标是验证 C8 int8 KV 量化在 KV 容量、推理吞吐和输出质量三个维度上的效果。实验使用 Qwen2.5-7B-Instruct 模型，同一权重（BF16，14.21 GiB），同一 HBM 预算（gpu_memory_utilization=0.92），同一 max_model_len=4096 和 max_num_seqs=64。唯一变量为 KV cache dtype：baseline 使用 BF16（FULL graph），C8 使用 int8（FULL_DECODE_ONLY graph，因 FULL decode 死锁）。

### 4.2.1 KV 容量与显存占用

引擎启动日志中的 GPU KV cache size 直接反映了相同 KV pool 预算下的 token 容量。结果如表 4-2 所示。

| KV dtype | KV pool 大小 | Token 容量 | 单 token 体积 |
|---|---|---|---|
| BF16（baseline） | 41.45 GiB | 775,936 | 1× |
| int8（C8） | 41.58 GiB | 1,556,992 | 0.5× |
| **倍率** | — | **2.007×** | — |

C8 在相同的 41.5 GiB KV pool 预算下实现了 2.007 倍的 token 容量提升。这是确定性的数学结果——int8 字节数为 BF16 的一半，容量翻倍不依赖实验波动。

### 4.2.2 吞吐与延迟对照

使用受控并发负载（固定 prompt 长度约 1,024 token，输出 128 token，ignore_eos=True 强制生满），分别在并发 16 和并发 32 条件下测量聚合吞吐和端到端延迟。

| 指标 | BF16 baseline | C8 int8 | 变化 |
|---|---|---|---|
| conc 16 聚合输出 tok/s | 616.5 | 830.3 | **+35%** |
| conc 16 e2e p50 | 2.45 s | 2.41 s | -1.6% |
| conc 16 e2e p95 | 5.08 s | 2.58 s | **-49%** |
| conc 32 聚合输出 tok/s | 1410.4 | 1443.2 | +2.3% |
| conc 32 e2e p50 | 2.87 s | 2.82 s | -1.7% |
| conc 32 e2e p95 | 2.94 s | 2.89 s | -1.7% |
| 完成率 | 48/48, 64/64 | 48/48, 64/64 | 100% 持平 |

C8 在两档并发下吞吐均不低于 BF16 baseline，conc 16 场景下甚至显著领先 35%，尾延迟（p95）在 conc 16 下降低 49%。原因分析：attention 计算是 KV-memory-bandwidth bound，int8 KV 将带宽需求减半，其收益在中等并发下超过了 FULL_DECODE_ONLY（decode eager）相对 FULL graph 的额外开销。在高并发（conc 32）下，带宽压力更为分散，C8 的吞吐优势收敛至 +2.3%。单次测量存在 NPU 状态波动，但 C8 不低于 BF16 的方向是稳定的。

### 4.2.3 输出质量验证

C8 的输出质量通过 post-RoPE 自校准 MinMax scale 保证。校准后 quant→dequant 的往返误差仅约 0.5%。同 prompt 抽检结果：7×8 返回 "56"、primary colors 返回 "red, blue, and yellow"、greeting 返回 "Hello and welcome!"——语义连贯正确，与 BF16 baseline 无差异。校准质量的关键验证数据见 5.1.2 节的表 5-1：post-RoPE 校准的逐层往返误差稳定在 0.4%-0.6%，而 pre-RoPE 校准在第 0 层误差高达 84.5% 且 68% 的值饱和截断。

## 4.3 F2 上下文压缩实验

F2 实验的目标是验证 context compression 在 Prompt token 节省和任务成功率两个核心维度上的效果，同时测量压缩延迟对端到端推理时间的影响。实验基于 τ-bench retail 数据集，使用 Qwen2.5-7B-Instruct 作为 Agent 模型，MIMO API 作为用户模拟器（正式评测），本地 7B 模型作为对照（早期消融）。

### 4.3.1 静态精简效果

静态精简（system prompt 压缩 + 工具描述去重）是 F2 中确定性、零运行时开销的部分。在 τ-bench retail 全量 115 任务中，使用最终配置（compact system/tools、hot 1k、cold 8k、LLMLingua-2），1,780 次模型调用全部受益于静态精简，完整 Prompt 从 10,933,355 token 降至 8,820,495 token，节省 2,112,860 token（降幅 **19.32%**）。本轮实验中动态 BERT 压缩触发 0 次——最大可压缩 cold body 仅 4,097 token，未达到 8,000 的触发门槛；也没有单个 hot tool result 达到 1,000 token。因此 19.32% 的降幅全部来自确定性静态精简。

### 4.3.2 动态压缩触发与复用

在 τ-bench retail 全量 115 任务并发 4 的实验中，F2 的动态压缩层统计数据为：74 次压缩 + 256 次复用 + 1,567 次 skip，复用率 78%。单次压缩均值 9.7 秒（gpt2，worker pool 4 + 限线程 32），总计压缩耗时约 718 秒。压缩比均值 1.95×（范围 1.48-2.75×），74/115 任务至少触发过一次压缩。

在非 retail 的通用长上下文 synthetic trace（28.9k token）上，动态 LLMLingua-2 触发压缩，Prompt 从 28,860 token 降至 20,936 token（降幅 **27.46%**）。首次 BERT 压缩耗时约 36 秒，相同 session 内复用约 5.9 毫秒。该实验证明了动态压缩在长上下文场景下的机制有效性——压缩确实发生，token 确实减少，复用确实生效。

### 4.3.3 全量 115 任务综合评测

τ-bench retail 全量 115 任务是 F2 的终极评测场景。baseline 和 F2 各运行一次（并发 4，MIMO user-sim），结果见表 4-3。

| 指标 | baseline (115) | F2 (115) | 变化 |
|---|---|---|---|
| 任务成功率 | 20.0%（23/115） | 22.6%（26/115） | **+2.6pp** |
| e2e p50 | 99.5 s | 109.1 s | +9.7% |
| e2e p95 | 156.1 s | 172.4 s | +10.4% |
| 上下文 token（冷区峰值表示） | 279,623 | 152,545 | **-45%** |
| KV 命中率 | 0.96 | 0.95 | -1pp |
| HBM 峰值 | 57,954 MB | 57,955 MB | 持平（vLLM 预分配池掩盖） |

成功率是不降反升的净赢（+2.6pp），跨多次独立 run F2 与 baseline 的成功率差在 ±3pp 内波动，属于噪声级别——**F2 不伤精度**。延迟 +9.7% 是 gpt2 压缩本身的耗时（~10 秒/任务），已通过 worker pool + 限线程从早期的 +16% 减半。剩余约 10% 的延迟代价需换 BERT（~3-5 秒/次）才能彻底消除。HBM 峰值被 vLLM 预分配池掩盖（启动即占满约 90% HBM），无法反映 -45% 上下文的实际显存收益。

### 4.3.4 Worker 池与压缩延迟消融

为量化不同压缩架构对延迟的影响，在 τ-bench retail 全量 115 任务上进行了三组消融对比：

| 配置 | 单次压缩耗时 | 总压缩耗时 | p50 延迟 vs baseline |
|---|---|---|---|
| 单 worker (gpt2, 不限线程) | 19.6 s | 1,452 s | **+16%** |
| worker pool 4 (gpt2, 不限线程) | 42 s | — | 更差（线程超订） |
| worker pool 4 (gpt2, 限线程 32) | **9.7 s** | ~718 s | **+9.7%** |

关键发现：gpt2 默认 64 线程在压缩小任务上纯亏——限线程后单次反而从 19.6 秒降至 9.7 秒。worker pool 4 + 限线程将延迟惩罚从 +16% 减半至 +9.7%。要彻底归零需换 LLMLingua-2 BERT（预期单次 3-5 秒，延迟惩罚预计降至 +3% 以内）。

## 4.4 F3 工具数据外置实验

F3 实验的目标是验证大规模工具结果外置后的 Prompt token 节省和检索正确率，以及在真实多跳问答场景中的端到端质量影响。

### 4.4.1 合成长结果 Prompt 节省

使用单次 360 条记录、18,658 Qwen token 的合成 JSON 工具结果，严格配对测量（同一轨迹、同一 tokenizer、同一 chat template），结果见表 4-4。

| 阶段 | 完整 Prompt token | vs baseline |
|---|---|---|
| baseline（inline 完整结果） | 21,350 | — |
| F2 only（压缩后 inline） | 17,075 | -20.02% |
| F3 only（外置为引用） | 1,499 | **-92.98%** |
| F2 + F3（组合） | 1,499 | **-92.98%** |

F3 将大工具结果从上下文中完全移除，仅保留不超过 222 token 的引用标记。vLLM server 端验证（3 轮 cache-busted，交替请求顺序）确认 server-reported usage 为 21,371 → 1,520 token（降幅 **92.89%**）。prefill 探针（1 output token）p50 从 1,822 ms 降至 81 ms——该数字仅测 prefill，不可外推为正常多轮 Agent 的端到端加速。

累计场景（3 次检索，每次 1 个 fetch）中，Prompt 从 57,570 token 降至 8,293 token（降幅 **85.59%**）。

### 4.4.2 受控检索正确率

使用 360 条记录的合成 JSON，目标记录分别位于索引 3（head）、180（middle）和 356（tail）。Qwen2.5-7B 需要自行识别引用标记、构造 fetch 参数、取回目标记录并返回验证码。结果见表 4-5。

| 配置 | 正确数 | 累计 Prompt token | vs baseline | fetch 次数 |
|---|---|---|---|---|
| baseline | 3/3 | 57,570 | — | 0 |
| F3 | **3/3** | 8,293 | -85.59% | 3 |
| F2+F3 | **3/3** | 8,295 | -85.59% | 3 |

F3 和 F2+F3 均在一次 fetch 内完成定位。模型自行生成 match_field/match_value 选择器，无需 benchmark 注入正确答案。该实验为受控精确 ID 查询，不证明任意语义检索质量无损。

### 4.4.3 2Wiki 多跳问答 100 题评测

LongBench 2WikiMultihopQA 前 100 题被改造为多轮工具检索 Agent 场景：文档集以 JSON 工具结果返回（baseline 完整 inline，F3/F2+F3 外置），Agent 通过检索和 fetch 完成两跳取证。所有配置使用同一本地 Qwen2.5-7B（vLLM-Ascend，max_model_len=32,768）。结果见表 4-6。

| 配置 | 正确 | 累计 Prompt | vs baseline | p50 模型请求总耗时 | 模型调用/题 | Context overflow 失败 |
|---|---|---|---|---|---|---|
| baseline | 31/100 | 1,632,665 | — | 1,269 ms | 240 / 2.40 | **5 次** |
| F3 | 31/100 | 554,657 | **-66.03%** | 1,726 ms | 368 / 3.68 | **0** |
| F2+F3 | 27/100 | 504,313 | **-69.11%** | 1,660 ms | 355 / 3.55 | **0** |

在 95 个 baseline 和 F3 都没有 request error 的任务对上，baseline 正确 31/95，F3 正确 30/95，双方独有成功 14/13，exact McNemar p=1.0——**本次未观察到严重或显著的 F3 质量下降**。F2+F3 的 27/100（-4pp vs baseline）未达统计显著但需复测。

F3 增加了模型调用次数（240 → 368，+53%），因为模型需要额外决定 fetch、生成工具参数、读取结果并继续推理。这些步骤串行执行，省下的 prefill 时间小于额外轮次的 HTTP、调度和 decode 成本，因此 p50 模型请求总耗时从 1,269 ms 增至 1,726 ms（**+36%**）。但 baseline 有 5 题因重复 inline retrieval 超过 32,768 context 而请求失败，F3/F2+F3 为 0——对于接近 context limit 的任务，F3 的首要价值从"是否更快"转为"是否可运行"。

### 4.4.4 存储与检索性能

F3 各操作的延迟基准（20 次 perf runs，p95）：SQLite externalize 8.53 ms、bounded fetch 5.08 ms、exact JSON search 0.15 ms、below-trigger passthrough 0.08 ms。所有操作均在毫秒级，远低于 LLM 推理延迟（秒级），对端到端时间的影响可忽略。外置引用最大 222 token（门限 512），fetch 响应最大 768 token（门限 768）。所有门限满足设计要求。

## 4.5 F4 分层存储实验

F4 实验的目标是验证 LMCache-Ascend 三级分层存储在 Agent 推理场景中的延迟和吞吐收益。

### 4.5.1 单 Agent 延迟与成功率

单 Agent 运行 10 个 τ-bench retail 任务，baseline vs f4-lmcache 对照结果见表 4-7。

| 指标 | baseline | f4-lmcache | 变化 |
|---|---|---|---|
| e2e p50 | 152.8 s | 120.8 s | **-21%** |
| 成功率 | 0.20 | 0.40 | +20pp |
| HBM 峰值 | 57,911 MB | 58,050 MB | +0.2% |

延迟降低 21% 来自 LMCache 的 KV 复用减少 prefill 重算。成功率提升 20pp 可能是轨迹差异（n=10 太小），不作为 F4 的因果归因。HBM 峰值几乎不变——τ-bench retail 的 prompt 约 7K token，并发 session 数少，KV cache pool 够用，LMCache 的 offload 层未被触发。

### 4.5.2 并发场景吞吐

并发 4 个 Agent session 同时运行，baseline vs f4-lmcache 对照结果见表 4-8。

| 指标 | baseline | f4-lmcache | 变化 |
|---|---|---|---|
| QPS | 0.028 | 0.037 | **+32%** |
| HBM 峰值 | 31,755 MB | 31,911 MB | +0.5% |

QPS 提升 32% 来自 LMCache 的 KV 复用减少了并发场景下的 prefill 竞争。HBM 峰值仍持平——如 4.5.1 节所述，τ-bench 的并发度和序列长度不足以触发 offload。LMCache 的显存收益需要更长序列或多并发才能体现。本次实验中 LMCache 主要发挥的是 KV 复用（CPU/Disk 层的 second-chance cache）而非 offload 作用。

## 4.6 F5 会话感知调度实验

F5 实验的目标是验证在并发 τ-bench 场景下，基于 HBM 准入控制和优先级调度对抢占消除、KV 命中率和端到端延迟的影响。实验使用 Qwen2.5-7B，刻意制造 HBM 压力——KV pool 仅分配 1.27 GiB（gpu_memory_utilization=0.27，max_model_len=16,384），6 并发 τ-bench retail × 25 steps，每组 runs=3 取中位数。

### 4.6.1 A/B/C 三组对照

三组对照：A 组为 vLLM 原生 FCFS（无优先级调度和准入控制）；B 组为 priority-static（所有 session 固定相同 priority，仅开启 --scheduling-policy priority）；C 组为动态回收（priority + KV-pool 准入控制）。结果见表 4-9。

| 指标 | A（FCFS） | B（priority-static） | C（动态回收） | C vs A |
|---|---|---|---|---|
| vLLM preemption | 有 | 有 | **0** | 消除抢占 |
| KV 命中率 | 0.48 | 0.46 | **0.93** | **+45-47pp** |
| e2e p50 | 114 s | 109 s | **90 s** | **-21%** |
| e2e p95 | 165 s | 158 s | 155 s | 略优 |
| TTFT | 152 ms | 132 ms | **111 ms** | **-27%** |
| mem_peak_mb | 17,399 | 17,401 | 17,401 | 同（pool 固定） |
| eviction-hit-idle | — | — | **100%**（3/3 run） | — |

**核心发现一：A ≈ B，priority 单独几乎不增益。** 静态 priority（所有 session 相同优先级）的调度行为与 FCFS 几乎一致——同优先级时退化为 LIFO。KV 命中率 B 组（0.46）甚至略低于 A 组（0.48），说明仅靠 priority flag 不解决问题。

**核心发现二：真正增益来自准入控制。** C 组的 KV-pool 准入控制实时监控 KV 利用率：当 KV 达到约 72% 时，num_requests_running 从 6 降至 3，KV 不再增长 → 不溢出 → **0 抢占**。A/B 组无闸门，KV 涨到 86-89% → preempt → 重算 → KV 命中率暴跌至约 0.46。C 组的 KV 命中率跃升至 0.93，e2e p50 降低 21%，TTFT 降低 27%。

**核心发现三：eviction-hit-idle 100%。** C 组在 3 次独立 run 中，所有驱逐均命中真正的 idle session（3/3，3/7，4/4 次全命中），证明空闲度检测准确、回收策略精准。

### 4.6.2 C vs D 无损卸载叠加

D 组在 C 组（准入控制）基础上叠加 SimpleCPUOffloadConnector（缝C），实现"准入控制消除抢占 + offload 降低 GPU KV 利用率"的协同效应。结果见表 4-10。

| 指标 | C（F5 only） | D（F5 + 无损 offload） | 变化 |
|---|---|---|---|
| e2e p50 | 90 s | **47 s** | **-48%（1.9× 更快）** |
| e2e p95 | 155 s | 126 s | -19% |
| QPS | 0.040 | 0.046 | **+16%** |
| mem_peak | 17,401 | 17,526 | ~同 |
| GPU KV 命中率 | 0.93 | 0.71 | 见下说明 |

GPU prefix-hit 从 0.93 降至 0.71 是假象：该指标只数 GPU 命中，不数 CPU 回读。offload 将冷 KV 搬到 CPU → GPU KV 利用率更低 → KV-pool 准入放开更高并发（C 把 running 压到约 3，D 能更高）→ p50 快 1.9×、QPS +16%。延迟变快证明确实净收益——CPU 回读成本远低于重算。

### 4.6.3 回收精准度与 KV 命中率分析

C 组实时 /metrics 抓取机制实证：KV 利用率上升到约 72% 时准入闸门触发，num_requests_running 从 6 降至 3。KV 利用率稳定在 70-75% 之间，不再突破。无抢占日志、无 preempt 计数器增长。

KV 命中率 0.93 的含义：在 C 组的准入保护下，活跃 session 的 KV block 保持在 GPU pool 中不被踢出，APC 持续命中。而 A/B 组的抢占→重算→KV 清零完全破坏了 APC 的缓存积累，命中率被打到约 0.46——约等于仅 system prompt 等固定前缀的命中率（即重算后 session 专属 KV 全部丢失）。

实验的诚实说明：成功率方面，C 组为 0、A 为 0、B 为 0.17（本地 7B user-sim 噪声，非 F5 问题）。"成功率不掉"的验证需外部 MIMO user-sim 补最终数据。mem_peak 在各组间无差异（KV pool 固定分配），F5 的显存收益体现在并发容量而非 pool 绝对值——准入控制使同等 HBM 下可承载更多 session 而不触发抢占。

## 4.7 多路径决策实验

MCTS 多路径决策实验的目标是定量测量 vLLM APC 的隐式 Copy-on-Write 在不同分支数下的 KV 复用效果，为分支推理场景的 KV 共享优化提供 baseline 数据。

### 4.7.1 分支数与 KV 命中率

实验在 HotpotQA distractor 验证集上取 30 题/组，设置五组对照，结果见表 4-11。

| 组 | prefix_cache | n_branches | KV 命中率（前/后） | 成功率 | 墙钟 | 请求数 | 生成 token |
|---|---|---|---|---|---|---|---|
| A | 关闭 | 2 | 0.682 / 0.706 | 43.3% | 207 s | 66 | 29,426 |
| B | 开启 | 1 | 0.706 / 0.733 | 40.0% | 153 s | 48 | 37,870 |
| C1 | 开启 | 2 | 0.733 / 0.736 | **53.3%** | 195 s | 72 | 51,231 |
| C2 | 开启 | 4 | 0.736 / 0.773 | **53.3%** | 516 s | 215 | 82,936 |
| C3 | 开启 | 8 | 0.773 / 0.800 | 46.7% | 814 s | 380 | 138,772 |

Prefix cache 开启组（B/C1/C2/C3）的 KV 命中率随分支数增加而逐步上升：B（73.3%）→ C1（73.6%）→ C2（77.3%）→ C3（80.0%）。这一趋势定性地验证了 APC 隐式 CoW 的预期——分支越多，共享前缀的 KV block 复用越多。但需注意定量局限性：引擎未在各组间独立重启，KV 命中率计数器跨组累加，存在累计假象。各组的"命中率前值"不等于前一组实验开始前的真实初始值。

### 4.7.2 搜索效率与成功率

C2 组（n_branches=4）在成功率（53.3%）和搜索效果的平衡上表现最优，与 C1 组并列最高。C3 组（n_branches=8）的成功率反而下降至 46.7%——过多的分支可能导致搜索空间过大、迭代次数不足（固定 max_iters=8）、LLM 动作质量下降。墙钟时间随分支数指数增长（B 153s → C3 814s），生成 token 从 37,870 增至 138,772。

TTFT 随分支数增加而降低（A 97.9ms → C3 63.0ms），原因是高分支数场景下 LLM 请求的 batch size 更大，prefill 阶段的矩阵乘效率更高。TPOT 各组分值接近（16-19 ms），说明 decode 阶段性能不受分支数影响。

### 4.8.3 局限性与诚实边界

**F1。** 单芯单次测量，绝对值有 NPU 状态波动；极低并发（conc=1）下的 C8 vs BF16 单 token 延迟未测。C8 不与投机采样、Mooncake PD 分离等特性叠加（存在已知冲突）。

**F2。** retail full115 的 19.32% 降幅全部来自静态精简，动态 BERT 在本轮 retail 中触发 0 次——这意味着对于工具结果较小、轮次较短的场景，F2 的收益上限由静态精简决定。非 retail 长上下文（28.9k synthetic trace）验证了动态压缩的机制有效性，但该 trace 是合成的，不代表真实 Agent 任务。延迟 +9.7% 的剩余代价来自 gpt2 压缩本身，需换 BERT 才能彻底消除。

**F3。** 2Wiki 评测中 baseline 正确率仅 31%，绝对水平偏低（Qwen2.5-7B 在无训练的多跳检索任务上的能力上限）。p50 模型请求总耗时 +36%，增量来自额外 fetch 轮次的串行 decode——F3 在 Prompt 和 context overflow 上是净赢，但在延迟上需参考任务特征。MIMO tau-bench retail 探针中 F3 外置 0 次（最大结果仅 1,416 token），该探针验证的是 F2+F3 兼容性而非 F3 收益。

**F4。** τ-bench 的并发度和序列长度不足以触发 LMCache 的 offload 层，内存峰值持平。F4 的实测收益在延迟和 QPS（KV 复用），显存收益需更长序列或多并发 workload 才能体现。

**F5。** 成功率因本地 7B user-sim 噪声接近零，A/B/C 组的成功率对比不能作为 F5 的质量证据。"成功率不掉"的验证需外部 MIMO user-sim 补最终数据。mem_peak 被 KV pool 固定分配掩盖，F5 的显存收益需用并发容量指标（同等 HBM 下最大可承载 session 数）来等价证明。

**MCTS。** KV 命中率为跨组累计值（引擎未在各组间独立重启），绝对值不可直接引用。实验规模小（30 题/组，单次运行），结果用于定性趋势分析而非定量结论。该方向为探索性测量而非已完成的优化模块。


# 第 5 章　实现难点说明

本系统基于 vllm-ascend 推理框架和华为 Ascend NPU 国产硬件平台构建，在实现过程中面临 Ascend 特有的底层算子适配、多版本 Python 环境隔离、Agent 协议的特殊结构保护、以及调度策略的实验驱动纠错等多方面挑战。以下就其中六个主要难点及其解决方法展开说明。

**一、Ascend C8 KV 量化的三坑突破**

F1 int8 KV Cache 量化在 Ascend 平台上的落地并非一帆风顺，先后遭遇三个紧密关联的技术障碍。第一个障碍是 FULL graph 死锁：C8 的 attention 路径走 `npu_fused_infer_attention_score` 配合 int8 分页 KV 和 per-channel antiquant，在 FULL ACL-graph capture 模式下对 decode 大 batch 存在确定性死锁——Qwen2 模型 batch≥26 时 NPU 进入 101W 空转状态且永远不会完成。排查发现死锁仅出现在 decode 阶段走 FULL graph 时，PIECEWISE 模式全程通过。解决方案是将编译模式改为 `FULL_DECODE_ONLY`——prefill 保持 FULL graph 以利用其计算优化，decode 退化到 eager 模式绕开死锁。由于 decode 阶段每次仅处理增量 token 且 int8 KV 带宽需求减半，eager 执行的额外开销被完全抵消。第二个障碍是校准精度：初次 C8 校准后模型输出为不可读的重复字符，一度被误判为 vllm-ascend 0.22.1rc1 的 C8 正确性 bug。实测定因发现校准脚本从 `k_proj`（pre-RoPE）采 scale，但 vLLM V1 存入 KV Cache 的是 post-RoPE 的 K 张量。RoPE 旋转将 Qwen3 第 0 层 K 的逐通道振幅放大 435 倍，pre-RoPE scale 因此偏小数个数量级，导致量化饱和截断（第 0 层 68% 的值超过 127），反量化严重错位。改为 monkeypatch `apply_rotary_pos_emb` 从 post-RoPE 位置采 scale 后，quant→dequant 往返误差降至约 0.5%，输出完全正确。第三个障碍是跨架构注入：Qwen2.5-7B 属于 Qwen2 架构，但 vllm-ascend 的 `patch_gqa_c8.py` 仅覆盖 Qwen3/Glm4Moe/MiniMaxM2。由于 vLLM V1 的 EngineCore 在独立子进程中加载模型，父进程的 monkeypatch 无法传播。解决方案是利用 Python 的 `sitecustomize.py` 机制——每个解释器启动时（包括 spawn 子进程）必定执行，通过环境变量 `QWEN2_C8_PATCH=1` 门控，在子进程启动瞬间自动注入 Qwen2 C8 scale 加载补丁。

**二、多版本环境隔离与依赖冲突**

本项目涉及 vLLM（推理引擎）、LLMLingua（压缩模型）、LMCache（分层存储）、τ-bench（测试环境）等多个软件组件的协同工作，各组件对 Python 包版本的要求存在显著冲突。最核心的冲突来自 transformers 库：vLLM 0.22.1 需要 transformers 5.x 的 `past_key_values` 新 API，而 LLMLingua 0.2.2 依赖 transformers 4.x 的旧 API，两者无法在同一 Python 进程中并存。解决思路是创建隔离的 `.venv-compress` 虚拟环境（transformers 4.43.4），将 LLMLingua 压缩任务委托给独立子进程执行，通过 JSONL stdin/stdout 实现主进程与压缩 worker 之间的轻量 RPC 通信。`_SubprocessCompressorPool` 维护多个常驻 worker 进程，LLMLingua-2 BERT 模型在每个 worker 中懒加载一次并跨请求复用，避免了每次压缩都重新加载模型的高昂开销。此外，numpy 2.4.6 版本的 ABI 变更（`dtype size changed`）导致依赖 sklearn/pandas 的 serving 栈崩溃，通过锁定 `numpy==1.26.4` 解决；lmcache 0.5.1 为 CUDA 编译版本，在 Ascend 平台无法使用，通过降级至 lmcache 0.4.4 并以 `NO_CUDA_EXT=1` 禁用 CUDA 扩展编译解决。开发过程中还发现一个反直觉的优化：gpt2 压缩 worker 默认 64 线程时单次压缩需约 20 秒，将线程数限制为 CPU 核数除以 worker 数（32 线程）后反而降至约 10 秒——小模型上过多线程的调度开销超过了并行收益。

**三、Agent 协议结构感知的上下文压缩**

标准文本压缩算法（如 LLMLingua-2）面向通用自然语言设计，对 Agent 推理中的 OpenAI 工具调用协议缺乏认知。该协议要求 assistant 消息中的 `tool_calls` 数组包含 `id`（调用标识）、`function.name`（工具名）和 `function.arguments`（调用参数）三个关键字段，且每个 assistant tool_call 必须与其对应的 `role=tool` 结果消息配对出现。若压缩错误地裁剪了 `call_id` 或修改了 `arguments` 中的 JSON 结构，工具调用将直接返回 API 400 错误。本项目的解决方案是在压缩前对历史消息进行物理拆分：protected prefix（user 消息全文、tool_calls 的 id/name/arguments、tool 消息的 call_id/name 以及按 JSON key 白名单匹配到的关键业务字段值）**完全不送入压缩器**，只有可压缩正文（assistant 的自然语言叙述和工具结果的描述性文本）才进入 LLMLingua-2。关键字段白名单覆盖了 Agent 推理中常见的 30 余个业务敏感字段模式（ID 类如 `order_id`/`product_id`、金额类如 `amount`/`price`/`total`、状态类如 `status`/`reason`、时间类如 `time`/`_at` 等），数值和布尔值也被自动保护。此外，冷热切分的边界必须前移至完整的 assistant-tool group，确保切分后的 cold history 不会产生孤立的 tool message，从而保证压缩前后消息序列始终满足 OpenAI API 的协议约束。

**四、结构化检索接口的正确性修复**

F3 模块的首版实现仅支持按行号和字符偏移进行分页取回。在以 360 条记录的 minified JSON（18,658 token，全部压缩为一行）进行端到端测试时，首版接口暴露了严重缺陷：Qwen2.5-7B 虽然正确调用了 `fetch_tool_result`，但行分页永远只能取到 JSON 文件的开头部分（因为全文仅有一行），导致 head/middle/tail 三项定位测试全部失败（0/3）。模型虽然表现出"调用 fetch"的正确意图，但接口无法将意图转化为有效的定位行为。修复方案是在 `fetch_tool_result` 中引入受限的结构化字段搜索功能：新增 `match_field`（目标字段名）、`match_value`（目标字段值）和 `match_mode`（匹配模式：exact/iexact/contains/icontains）三个参数。在 360 条记录的 JSON 数组中，Qwen2.5-7B 仅需一次 fetch 即可根据用户给出的 `case_id` 自行生成正确的字段选择器并取回目标记录的数据。修复后 head/middle/tail 三项测试全部通过（3/3），F2+F3 组合模式同样 3/3。为避免安全风险，字段搜索不支持正则表达式、JSONPath 表达式或任意代码执行，仅限四种确定性的字符串匹配模式，单次返回最多 10 条结果，所有响应受 768-token 硬上限约束。

**五、会话感知调度的关键发现**

F5 模块最初的设计假设是：开启 vLLM 的 `--scheduling-policy priority` 并给 idle session 分配更高的 priority 值，即可让 vLLM 在 HBM 满时优先淘汰空闲会话而非活跃会话。然而 A/B/C 三组对照实验揭示了与预期不符的事实：A 组（FCFS，无 priority）和 B 组（priority-static，所有 session 相同 priority）表现几乎相同——KV 命中率分别为 0.48 和 0.46，端到端 P50 延迟分别为 114 秒和 109 秒。这意味着静态 priority 单独使用几乎不产生增益，因为在同优先级时调度器退化为 LIFO。真正的增益来源于 C 组叠加的 KV-pool 准入控制器：当实时监控到 KV pool 利用率达到约 72% 时，准入控制器主动将运行中的并发数从 6 降至 3，使 KV 不再增长、永不溢出、永不触发抢占。这直接使 KV 命中率从 0.46-0.48 跃升至 0.93，端到端 P50 延迟降低 21%。这一发现促使我们将 F5 的设计重心从"优化驱逐选择"调整为"防止驱逐发生"——准入控制比优先级调度更为根本。

**六、NPU 卸载路径的废弃识别与正确选型**

F5 Phase 2 的目标是在准入控制之上叠加无损 KV 卸载（冷 KV → CPU，命中时回读）。最初的调研方向是使用 `NPUOffloadingSpec`/`OffloadingConnector` 路径，并评估是否需要升级 vllm-ascend 版本或 fork 仓库来实现。深入源码分析后获得了三个关键发现：该路径在 vllm-ascend 自身的端到端测试中被标记为 `@pytest.mark.skip(reason="cpu offload connector is deprecated.")`；在 0.22.1rc1 版本上存在 import drift（`abstract`/`mediums`/`spec` 模块路径已变更）和架构 drift（`CanonicalKVCaches` vs 旧 `dict[str,Tensor]` 的 assert 失败）；0.23.0rc1 的发布说明中将其列为 "Ready to Deprecate"。这三个发现一致指向同一个结论：`NPUOffloadingSpec` 是已被上游放弃的废弃路径，升级版本无法解决问题，fork 修复毫无意义。转而分析当前版本自带的 `SimpleCPUOffloadConnector`——其在 vllm-ascend `__init__.py` 中自动将上游的 CUDA worker 替换为 NPU worker（`AscendSimpleCPUOffloadConnector`），使用 `aclrtMemcpyBatchAsync` + `torch.npu.Stream` 实现真正的 NPU↔CPU 异步传输，且正确处理 Ascend 的 K/V 分离存储和 2 MiB 内存对齐。确认该路径可用后，D 组实验成功将准入控制叠加无损卸载，P50 延迟从 C 组的 90 秒进一步降至 47 秒（提升 1.9 倍）。这一过程积累了一条重要经验：在 Ascend 平台上做技术选型时，须以实测和源码为准，不能依赖文档描述或上游 roadmap 的预期。

上述是团队在实现本系统过程中遇到的主要技术难点，同时还有许多其他工程问题，如 vLLM stub server 的无 NPU 联调方案、20 个 yaml 配置预设的白名单校验机制、中间件栈的七个钩子协议设计和跨 session 并发安全等，均在团队成员的共同努力下被逐一克服。


# 第 6 章　总结

本文围绕"面向智能体的内存管理系统"这一赛题，基于 vllm-ascend 开源推理框架和华为 Ascend 910B2C NPU 国产硬件平台，针对 LLM Agent 长生命周期推理中 KV Cache 持续累积、上下文高度冗余、推理路径分支、工具调用大数据和内存生命周期长五大特征，设计并实现了覆盖五个技术方向的系统性内存优化方案。

在 KV Cache 量化方面，本文在 Ascend NPU 上实现了 C8 int8 量化，通过 post-RoPE 逐通道 MinMax 自校准和 FULL_DECODE_ONLY 图编译模式适配，在 Qwen2.5-7B 上实现 KV token 容量翻倍（775,936 → 1,556,992），并发 16 场景下聚合吞吐提升 35%，尾延迟降低 49%。在上下文压缩方面，提出了 Agent 协议感知的 tool-aware 压缩框架，通过确定性静态精简与 LLMLingua-2 动态压缩的分层组合，在 τ-bench retail 全量 115 任务上实现完整 Prompt token 降低 19.32%，成功率不降反升。在工具数据外置方面，设计了 session-scoped SQLite ArtifactStore 与受限结构化检索接口，在合成长结果场景下 Prompt 降低 92.98%，在 2Wiki 100 题多跳问答中累计 Prompt 降低 66.03% 且正确率持平，同时消除了 context overflow 导致的请求失败。在分层存储方面，完成了 LMCache-Ascend 的集成与配置，单 Agent 场景延迟降低 21%，并发场景吞吐提升 32%。在会话感知调度方面，设计了 HBM 驱动的滞回准入控制器与空闲感知优先级策略，实现了抢占次数的完全消除和 KV Cache 命中率从 0.46 跃升至 0.93，叠加 SimpleCPUOffloadConnector 后 P50 延迟降至 47 秒。

在工程实现层面，本文构建了完整的系统基础设施：自写 ReAct Agent 循环支持多轮工具调用与流式推理；基于 Runner Protocol 的模块化 Benchmark Harness 支持六项核心指标的自动采集和三档对照实验；20 个 yaml 配置预设实现各功能的独立开关和参数隔离；Gradio 实时展示前端提供多类型 benchmark 的一键运行和指标可视化。全部实验数据均在 Ascend 910B2C NPU 和 openEuler 24.03 国产平台上实测获得，可完整复现。

本文工作尚存在若干不足。F2 的动态压缩在 retail 场景中 BERT 触发为零，19.32% 的 Prompt 降幅全部来自静态精简，动态压缩的收益上限尚未在真实 Agent 长会话任务中验证；剩余约 10% 的端到端延迟代价需从 gpt2 迁移至 LLMLingua-2 BERT 才能彻底消除。F3 在缩短 Prompt 的同时增加了模型调用轮次，在 2Wiki 场景中延迟增加 36%，额外的 fetch 串行开销是当前方案的主要代价。F4 在 τ-bench 的并发度和序列长度下 offload 层未被触发，显存收益需更长序列或多并发 workload 验证。F5 的成功率因本地 user-sim 噪声未能有效测量。F6（KV Checkpoint）、F7（分支 KV 共享完整分析）、F8（多硬件对照）、F9（国产 OS 容器化部署）四个模块仍处于设计或待执行状态。MCTS 多路径决策实验仅完成探索性测量，KV 命中率数据存在累计假象，尚不能作为定量结论。

未来工作将围绕以下几个方向展开：将 F2 动态压缩后端从 gpt2 迁移至 BERT，彻底消除延迟代价；为 F3 的 fetch 接口扩充多字段 AND/OR 和数值范围查询，减少模型往返轮次；在更长序列或更高并发 workload 上验证 F4 的 offload 层显存收益；在外部 MIMO user-sim 下补全 F5 的成功率对照数据；完成 F6-F9 四个模块的实现与评测；基于 MCTS 分支 KV 复用数据，探索独立引擎重启下的准确命中率测量。我们相信，随着国产 AI 硬件生态的持续成熟和推理框架的不断演进，面向智能体的内存管理优化将迎来更大的发展空间。
