# 第 1 章　绪论

## 1.1 目的与意义

本作品是一个面向大语言模型智能体的内存管理系统，部署于华为 Ascend NPU 国产 AI 加速硬件和 openEuler 国产操作系统之上，旨在解决 LLM Agent 长生命周期推理过程中的显存瓶颈问题。

随着基于大语言模型的智能体系统不断发展，其推理范式已由传统的单轮生成扩展为涵盖规划、执行与反思的长生命周期复杂过程。在这一过程中，智能体需要进行多轮动态交互，频繁调用工具与外部环境，导致 KV Cache 持续累积、上下文高度冗余、工具调用产生大规模中间数据。传统推理框架（如 vLLM）主要面向线性序列生成场景进行优化，缺乏对智能体长生命周期、多轮对话和分支推理等特有模式的内存管理策略。

本作品针对上述问题，基于 vllm-ascend 开源推理框架，设计并实现了覆盖 KV Cache 量化、上下文压缩、工具数据外置、分层存储和会话感知调度五个技术方向的系统优化方案。在保证任务成功率基本不下降的前提下，有效降低了显存占用并提升了推理效率。本作品的全部工作部署于国产 Ascend 910B2C NPU 和 openEuler 24.03 操作系统之上，对于推动国产 AI 硬件在智能体推理领域的应用、探索面向 Agent 特征的内存管理优化技术具有积极的实践意义。

## 1.2 项目背景

当前主流的 LLM 推理引擎在内存管理方面已经取得了显著进展。vLLM 提出的 PagedAttention 机制借鉴了操作系统的分页管理思想，通过 block 级的内存分配和自动前缀缓存（APC）大幅减少了 KV Cache 的内存碎片和冗余存储。llama.cpp 支持多种 KV Cache 量化格式以降低内存占用。SGLang 提出的 RadixAttention 基于 radix 树结构实现了更灵活的跨请求前缀共享。

然而，上述方案主要面向通用推理场景设计，对于 LLM Agent 推理的独特内存特征缺乏针对性优化。Agent 推理与普通推理存在五点本质差异：第一，多轮对话导致 KV Cache 随轮次持续累积，单会话寿命远超 single-shot 请求；第二，系统提示和工具定义每轮重复发送，上下文存在高度冗余；第三，推理路径可能出现分支（如自洽性或树搜索策略），分支后的独立 KV Cache 导致显存成倍增长；第四，工具调用返回的大规模结构化数据被完整放入上下文，进一步加剧 KV 膨胀；第五，多会话并发场景下，不同会话的活跃度存在差异，原生调度器缺乏会话感知能力导致非必要的抢占和重算。

针对上述问题，业界已有部分探索。LLMLingua 系列工作提供了基于小型语言模型的 token 级上下文压缩方法，但其面向通用文本设计，无法保护 Agent 工具调用协议中的结构化字段。LMCache 实现了 GPU→CPU→Disk 三级 KV 分层存储，但主要面向 CUDA 生态。ByteDance 的 DeerFlow 提出了工具输出预算管理的基本范式，但依赖 LangChain/LangGraph 运行时且检索接口以行分页为主。这些方案各自独立解决单一问题，尚未形成面向 Agent 推理全流程的系统性内存管理方案。

更为关键的是，上述工作绝大多数在 NVIDIA CUDA 平台上开发验证，在国产 AI 硬件平台上缺乏可用的实现和基准数据。vllm-ascend 虽然将 vLLM 适配到了 Ascend NPU，但在智能体推理的内存优化方面仍处于空白状态——KV Cache 量化、上下文压缩、工具数据管理和会话调度等关键能力均未在国产平台上得到验证。本作品正是在这一背景下，以 openEuler 操作系统和 Ascend NPU 为底座，将五个优化方向在国产技术栈上首次完整落地，为国产 AI 硬件在智能体推理场景中的应用提供了可复现的系统方案和实测基准。

本作品的主要新颖之处在于：第一，在 Ascend NPU 上首次实现了 int8 KV Cache 量化（C8），通过自主设计的 post-RoPE 逐通道 MinMax 自校准方法解决了 Ascend 硬件特有的精度和死锁问题，实现 KV 容量翻倍且吞吐不降，填补了国产平台上 KV Cache 量化的空白；第二，提出了 Agent 协议结构感知的上下文压缩方法，在标准压缩算法基础上增加了对 OpenAI 工具调用协议的完整性保护，兼顾压缩效率和任务成功率；第三，将 KV 量化、上下文压缩、工具数据外置、分层存储和会话感知调度五个方向整合为统一的"稳定缝 + 独立功能"模块化架构，每个功能可独立开关、独立评测、独立交付，形成了一套面向国产 AI 推理平台的、可扩展的智能体内存管理解决方案。


# 第 2 章　技术理论

## 2.1 设计思想

本系统在设计上遵循"稳定缝 + 独立功能"的模块化方法。稳定缝指系统中存在的一个稳定接口位置——位于同一缝上的功能模块共享接口约束但彼此独立，一个功能的开关不影响同缝其他功能的运行。系统定义了七条稳定缝：缝A（引擎 flag 预设）承载 KV 量化配置，缝B（引擎后端）承载多硬件切换，缝C（KV connector）承载分层存储和卸载配置，缝D（上下文中间件）承载上下文压缩和工具数据外置，缝E（Session 生命周期策略）承载会话调度和 checkpoint，缝F 承载多路径决策实验工作流，缝G 承载国产化容器部署。

这一设计方法的核心价值在于解耦。不同缝的功能天然独立——例如 F1 在缝A 修改 vLLM CLI 参数，F3 在缝D 修改对话 messages，两者互不干涉。同缝内的功能通过独立 yaml 配置隔离——例如 F2 和 F3 同在缝D，`middleware.active: [compress]` 和 `middleware.active: [lazyload]` 可独立开关。每个功能拥有独立的 yaml 预设、独立的前后对照数据、独立的单元测试，可单独交付而不依赖其他功能的完成状态。这种架构设计使三人团队可以并行开发五个功能模块，大幅提升了开发效率。

## 2.2 技术路线

本系统采用四层架构。底层为国产化部署层：基于 openEuler 24.03 和 Ascend 910B2C NPU，通过 CANN 9.0.0 软件栈和 torch_npu 2.10.0 提供 AI 算力。第二层为推理引擎层：vLLM V1 架构作为推理内核，vllm-ascend 0.22.1rc1 作为 Ascend 适配插件，通过 OpenAI-compatible API 向上层提供统一推理服务。第三层为 Agent 推理层：自写 ReAct 循环实现多轮工具调用的完整流程，通过有序 MiddlewareStack 在模型请求前后和工具结果返回后插入变换逻辑。第四层为 Benchmark 评测层：基于 Runner Protocol 的可插拔评测框架，支持 τ-bench 和 LongBench 两类标准化 Benchmark。

核心技术选型包括：Agent 模型使用 Qwen2.5-7B-Instruct（BF16，Qwen2 架构，GQA 4 KV heads），上下文压缩使用 LLMLingua-2 multilingual BERT（CPU 推理，不占用 NPU），分层存储使用 LMCache-Ascend 社区插件（NPU 原生，GPU→CPU→Disk 三级），实验评测使用 τ-bench retail 和 LongBench 2WikiMultihopQA 数据集。

系统采用"配置驱动"的工作模式。所有功能模块的参数通过 20 个 yaml 预设文件管理，`vllm_server.py` 的 `build_serve_args()` 函数自动将声明式配置翻译为 vLLM CLI 参数。每次 Benchmark 运行自动创建标准化 run 目录，记录 config.yaml 复本、git commit hash、pip freeze 环境快照和 NPU 硬件信息，确保任意历史实验可完整追溯和复现。

## 2.3 代码原创说明

本作品的全部代码存放于 `agent-mem/src/agent_mem/` 目录下，核心模块及代码来源分类如下：

**自研模块（本团队独立开发）。** Agent 推理循环（`agent/react.py`、`agent/tau_bench_agent.py`）为自写 ReAct 实现，不依赖 LangChain、LangGraph 或 Qwen-Agent 的 Assistant。中间件栈（`middleware/base.py`）的 Middleware Protocol、MiddlewareStack 有序链和七个钩子接口为自研设计。上下文压缩中间件（`middleware/compress.py`）的冷热分层切分算法、双阈值增量复用策略、tool-aware 序列化拆分与关键字段白名单保护、JSONL 子进程 RPC worker 池为自研实现。静态 prompt 精简（`middleware/static_prompt.py`）的 COMPACT_RETAIL_POLICY、工具描述去重（C1/C2 convention）和通用 policy 编译/校验为自研实现。工具数据外置中间件（`middleware/lazyload.py`）的 SQLite/Memory ArtifactStore、确定性结构摘要（`middleware/tool_synopsis.py`）、RFC 6901 JSON Pointer + 字段搜索的受限检索接口为自研实现，设计参考了 ByteDance DeerFlow 的 ToolOutputBudgetMiddleware 架构思想但未复制其代码。会话调度模块（`scheduler/`）的 SessionManager、AdmissionController 滞回准入、PriorityEvictionStrategy 和 ConcurrentSessionDriver 为自研实现。KV 量化工具链（`kv/c8.py`）的 C8 模型标注/还原/探针函数为自研实现。C8 post-RoPE 校准脚本（`scripts/calibrate_c8_qwen2.py`）和 Qwen2 sitecustomize 注入补丁（`kv/c8patch/sitecustomize.py`）为自研实现。配置系统（`config.py`）、复现系统（`repro.py`）、流式 TTFT 测量（`agent/react.py` 中的 `stream_chat_with_ttft`）、上下文遥测（`context_telemetry.py`）为自研实现。Benchmark 评测框架（`bench/`）的 Runner Protocol、SuiteAdapter 抽象层、三档对照与门槛判定（`bench/compare.py`）为自研实现。MCTS 实验脚本（`scripts/lats_hotpot_offline.py`、`scripts/offline_hotpot_env.py`、`scripts/run_baseline.py`）为自研实现，其中 MCTS 算法参考了 Princeton LATS 论文的算法描述但所有代码为独立编写。Gradio 展示前端（`demo/`）的 chat_app.py（~1,569 行）、EngineManager、LiveMonitor 为自研实现。KV connector 配置模块（`kv/connector.py`）的声明式配置翻译和 flat JSON schema 适配为自研实现。

**直接调用的开源组件。** 压缩算法核心调用 Microsoft LLMLingua / LLMLingua-2 的 `llmlingua.PromptCompressor`（对应 `middleware/compress.py` 中的 `_SubprocessCompressor` 和 `_SubprocessCompressorPool` 类，约 300 行代码负责 worker 管理和 RPC 通信，压缩本身由 LLMLingua 库完成）。LMCache 可用性探测调用 `lmcache_ascend` 包（`kv/lmcache_check.py`，约 30 行）。推理引擎封装调用 vllm-ascend 的 API Server（`server/vllm_server.py` 通过子进程方式管理其生命周期，约 200 行）。benchmark 适配器调用 τ-bench 的 retail/airline 环境和 LongBench 的 2WikiMultihopQA 数据（`bench/tasks/tau_bench_adapter.py` 约 250 行、`longbench_adapter.py` 约 180 行）。前端调用 Gradio 5 + Plotly 框架（`demo/chat_app.py`、`demo/monitor.py`，均为自研 UI 逻辑，调用 Gradio/Plotly API）。Python 标准库中的 `sqlite3`、`json`、`csv`、`html.parser` 用于 F3 的持久化存储和确定性解析。

**参考设计但未复制代码。** F3 的架构参考了 ByteDance DeerFlow 的 `ToolOutputBudgetMiddleware` 设计思想（per-tool output budget、持久化、compact synopsis、bounded retrieval），但未 import、vendor 或复制 DeerFlow/LangChain/LangGraph 的任何代码。MCTS 算法参考了 Princeton LATS 论文和 `LanguageAgentTreeSearch` 参考实现的结构，但为适配离线 HotpotQA 环境和 v3 改进（Finish 不截断、确定性 rollout、全树答案提取）而完全独立编写。

**测试与工具脚本。** `scripts/` 目录下的 C8 校准脚本、F5 实验编排器、MCTS 实验脚本均为自研。`benchmarks/` 目录下的 F3 检索质量/多跳评测/长工具基准脚本均为自研。`tests/` 目录下 37 个测试文件的测试逻辑为自研。


# 第 3 章　项目介绍

## 3.1 总体功能介绍

本系统是一个面向 LLM Agent 推理的内存管理优化平台，提供从底层 KV Cache 量化到上层上下文治理、从单 session 到多 session 并发的全流程优化能力。系统由四层架构组成：国产化部署层（openEuler + Ascend NPU + CANN）、推理引擎层（vLLM V1 + vllm-ascend）、Agent 推理层（自写 ReAct + 中间件栈）和 Benchmark 评测层（Runner Protocol + 三档对照）。系统的核心优化能力由五个独立功能模块（F1-F5）和一个探索性实验系统提供，外加一个 Gradio 实时展示前端。

各模块的功能分工如下：F1（KV Cache 量化）负责将 BF16 格式的 KV Cache 压缩为 int8，使同等显存下 KV token 容量翻倍。F2（上下文压缩）负责对 Agent 推理中每轮重复发送的 system prompt/tools schema 和累积的对话历史进行压缩，降低 Prompt token 占用。F3（工具数据外置）负责将大规模工具返回结果从上下文移入外部存储，通过结构化引用和受限检索接口按需取回。F4（分层存储）负责将冷 KV block 从 GPU 卸载到 CPU/Disk，突破 HBM 容量限制。F5（会话感知调度）负责在多 session 并发时按会话空闲度动态调整优先级和并发数，消除随机抢占和缓存失效。MCTS 实验系统负责在不同分支数下测量 vLLM APC 的 KV 复用效果。展示前端提供多类型 Benchmark 的一键运行、功能模块效果对比和指标实时可视化。

## 3.2 KV Cache 量化模块（F1）

F1 模块将 KV Cache 从 BF16 量化到 int8（Ascend 上称为 C8），使 41.5 GiB KV pool 的 token 容量从 775,936 翻倍至 1,556,992。模块由三个组件构成。

**C8 注入工具链。** `agent_mem/kv/c8.py` 提供四个纯函数 CLI 命令：`annotate_model()` 向模型目录写入 `quant_model_description.json` 标记 `kv_cache_type: "C8"`；`inject_placeholder_scales()` 注入占位 scale 供探针验证；`restore_model()` 还原 stock 模型；`is_annotated()` 检测 C8 标注状态。工具链不依赖 NPU，可在 CPU 环境通过单元测试完全验证。

**post-RoPE 自校准。** `scripts/calibrate_c8_qwen2.py` 在 NPU 上运行 32 条校准样本，monkeypatch `apply_rotary_pos_emb` 从 post-RoPE 位置捕获 K 的逐通道 maxabs（V 无 RoPE 直采 `v_proj`），计算 per-channel scale = max(|x|)/127 并注入 safetensors。calibrate_c8_qwen2.py 针对 Qwen2 架构，head_dim 手动推导（无 `config.head_dim` 字段）、ch=512。

**Qwen2 子进程注入。** `c8patch/sitecustomize.py` 利用 Python sitecustomize 机制（每个解释器启动必跑）monkeypatch `Qwen2ForCausalLM.load_weights`，使 C8 scale 在 vLLM EngineCore 子进程中正确加载。通过 `QWEN2_C8_PATCH=1` 环境变量门控。引擎配置由 `f1-bench-c8.yaml` 驱动，自动注入 `--quantization ascend` + `FULL_DECODE_ONLY` 编译模式。

## 3.3 上下文压缩模块（F2）

F2 模块通过确定性静态精简和 LLMLingua-2 动态压缩两层策略，降低 Agent 推理的 Prompt token 占用。

**静态精简层。** 在 Agent 初始化时一次性完成，零运行时开销。System prompt 精简：τ-bench retail 原始 policy 约 1,188 token，人工审计的精简版约 445 token（节省 63%）。通用场景支持离线编译 policy artifact（`compile_policy.py`），加载时进行 source hash、字面量和模态词三重确定性校验，失败自动回退。工具描述去重：扫描 tools schema 中所有 description 字段，重复内容提取为 C1/C2/... 共享约定在 system prompt 中出现一次，原处替换为 See Cn. 引用。

**动态压缩层。** `CompressMiddleware` 实现冷热分层压缩。冷热切分算法以最近 6 条消息为 hot tail，边界前移确保 assistant tool_call 与 tool result 配成完整消息组。冷区正文累计达到 8,000 token 时触发首次压缩，之后每累积 4,000 token 重新压缩，冻结期内后续请求直接复用。tool-aware 保护机制在压缩前将消息拆分为 protected prefix（user 消息 + tool_calls 结构 + 关键字段，100% 不送压缩器）和 compressible body（自然语言叙述，assistant 保留率 75%，tool result 保留率 60%）。压缩在隔离 `.venv-compress` 子进程中执行，worker pool 支持任务级并行，LLMLingua-2 BERT 模型懒加载一次跨请求复用。三级缓存（session 级冻结段 / 压缩结果 / token count）将缓存命中延迟降至约 6 毫秒。

## 3.4 工具数据外置模块（F3）

F3 模块将超过 4,000 token 的工具返回结果从对话上下文移入外部存储，在 Agent 历史中仅保留轻量引用标记。

**ArtifactStore 存储层。** 定义统一协议（`store`/`fetch`/`delete`/`sweep_expired`）和两种后端：MemoryArtifactStore（线程安全，用于单测）和 SQLiteArtifactStore（持久化，`(session_id, result_id)` 联合主键，WAL 模式，写入 SHA-256 校验，TTL 自动清理）。

**外置决策与确定性摘要。** 工具结果返回后使用 Qwen tokenizer 精确计算 token 数，达到 4,000 token 门槛则存入 store 并生成引用标记。摘要由 Python 标准库确定性生成（JSON → shape/key/array pointer/title，HTML → heading 列表，CSV → columns），不调用 LLM。仅当引用比原文短且不超过 512 token 时才执行替换。

**受限结构化检索。** `fetch_tool_result` 内部工具支持 RFC 6901 JSON Pointer 定位、单字段匹配搜索（exact/iexact/contains/icontains，最多 10 条含稳定 `match_pointers`）、行/字符分页。所有响应受 768-token 硬上限约束，字段搜索不支持正则或 JSONPath。工具调用在中间件栈内部处理不经过 τ-bench 环境。

## 3.5 分层存储模块（F4）

F4 模块通过 LMCache-Ascend 实现 GPU（NPU）→CPU→Disk 三级 KV Cache 分层存储。LMCacheAscendConnector 已在 vllm-ascend 0.22.1rc1 的 KVConnectorFactory 中注册，本模块的工作聚焦于环境适配和配置封装。环境方面：Ascend 910B2C 需设置 `SOC_VERSION=Ascend910B2C`，lmcache 降级为 0.4.4 并禁用 CUDA 编译（`NO_CUDA_EXT=1`）。配置方面：`f4-lmcache.yaml` 封装声明式参数，`build_serve_args()` 自动翻译为 `--kv-transfer-config` CLI JSON。LMCache 对上层 Agent 和推理代码完全透明。备选降级方案为 `kv_offload.yaml`。

## 3.6 会话感知调度模块（F5）

F5 模块解决多 Agent session 并发时的随机抢占和缓存失效问题。模块由四个核心组件和一个 Phase 2 叠加层构成。

**SessionManager。** 线程安全的会话注册中心，定义四态状态机（ACTIVE → OFFLOADED → CHECKPOINTED → EVICTED），追踪每个 session 的最后活跃时间戳。

**AdmissionController。** HBM 驱动的滞回准入控制。通过可注入的 MemBackend 接口实时读取 HBM 利用率，按 target_lo=70%/target_hi=85% 双阈值决策。拒绝准入时选出最空闲 session，将其 priority 设为 100 触发 vLLM priority 抢占。MemBackend 支持 TorchNpuBackend、NpuSmiBackend 和 FakeBackend 三种实现，使准入控制器可在无 NPU 环境完整测试。

**PriorityEvictionStrategy。** idle 超阈值 session → priority=100（可淘汰），active session → priority=0（受保护）。通过 `priority_fn` 和 `on_turn_start` 两个回调注入每个 Agent 任务，priority 透传至 vLLM 引擎的 `extra_body` 字段。

**ConcurrentSessionDriver。** 串起上述三者的编排器，后台 sweep 线程定期扫描 idle session 并触发优先级调整。EvictionTracker 线程安全记录驱逐命中 idle 的比例。

**Phase 2 无损卸载叠加。** 在准入控制之上叠加 SimpleCPUOffloadConnector（缝C），冷 KV 在 LRU 淘汰前异步拷贝到 CPU（`aclrtMemcpyBatchAsync` + 独立 `torch.npu.Stream`），命中时从 CPU 回读。CPU 回读成本约重算的 1/1000。

## 3.7 多路径决策实验系统

MCTS 实验系统用于定量测量 vLLM APC 在不同分支数下的 KV 复用效果。`OfflineHotpotEnv` 提供基于 HotpotQA distractor 数据集的离线检索环境（TF-IDF 索引，Search/Lookup/Finish 三动作），替代了原始 LATS 的实时 Wikipedia API 依赖。`mcts_search()` 实现四阶段 MCTS（UCT 选择 → LLM 扩展 → 确定性 Rollout → 回传），v3 改进包括 Finish 不截断、确定性 rollout（temperature=0）、全树答案提取。实验设置 A/B/C1/C2/C3 五组，分别对应无 prefix cache 和 prefix cache 开启下的 1/2/4/8 分支。该系统定位为对分支 KV 共享的探索性测量工具。

# 第 4 章　实验测试

## 4.1 测试说明

全部测试在统一环境下完成：华为 Ascend 910B2C NPU（64 GB HBM），openEuler 24.03，CANN 9.0.0 + torch_npu 2.10.0.post2，vllm-ascend 0.22.1rc1（editable 安装），Qwen2.5-7B-Instruct（BF16）。实验使用 τ-bench retail（115 任务）、LongBench 2WikiMultihopQA（100 题）和 HotpotQA distractor（30 题/组 × 5 组）三个数据集。

评测指标覆盖六个维度：端到端延迟（P50/P95）、每秒查询数（QPS）、HBM 峰值占用、KV Cache 前缀命中率、任务成功率和首 token 时间（TTFT）。指标通过四个通道并行采集：Runner 框架、MemSampler 后台轮询、vLLM /metrics 端点解析和事件日志。所有功能模块遵循统一的对照实验规范：同一硬件和模型、仅改变待测模块开关，每组配置独立运行 3 次取中位数。对照报告自动计算各指标变化率并与预设门槛比较：显存降幅 ≥ 30%、延迟改善 ≥ 20%、成功率差 ≤ 2 个百分点。

## 4.2 测试结果

**F1 C8 int8 KV 量化。** 相同 41.5 GiB KV pool 预算下，C8 的 token 容量为 1,556,992（BF16 baseline: 775,936），实现 2.007× 容量提升。受控并发负载测试中，并发 16 时 C8 聚合吞吐 830.3 tok/s（baseline 616.5 tok/s，+35%），P95 尾延迟 2.58 s（baseline 5.08 s，-49%）。并发 32 时吞吐 1,443.2 tok/s（baseline 1,410.4 tok/s，+2.3%）。输出质量经 post-RoPE 自校准保证，quant→dequant 往返误差约 0.5%，常识和算术推理输出连贯正确。

**F2 上下文压缩。** τ-bench retail 全量 115 任务（并发 4），完整 Prompt 从 10,933,355 token 降至 8,820,495 token，降幅 19.32%（全部来自静态精简，1,780/1,780 次调用均有收益）。任务成功率从 23/115 变为 26/115（+2.6pp，F2 不伤精度）。端到端 P50 延迟 +9.7%（99.5s → 109.1s），代价来自 gpt2 压缩耗时（worker pool 4 + 限线程，单次均值 9.7s），换 BERT 可进一步消除。

**F3 工具数据外置。** 合成 360 条记录大 JSON（18,658 token），F3 将上下文从 21,350 token 降至 1,499 token（降幅 92.98%）。受控头/中/尾检索正确率 3/3（baseline/F3/F2+F3 均 3/3）。2Wiki 多跳问答 100 题：F3 累计 Prompt 从 1,632,665 token 降至 554,657 token（-66.03%），正确率与 baseline 持平（31/100），context overflow 失败从 5 次降至 0 次。增量来自额外 fetch 轮次（240 → 368 次模型调用），模型请求总耗时 P50 +36%。

**F4 分层存储。** 单 Agent 10 任务：e2e P50 延迟从 152.8 s 降至 120.8 s（-21%）。并发 4 Agent：QPS 从 0.028 升至 0.037（+32%）。HBM 峰值在两项测试中均持平——τ-bench prompt 约 7K token，并发度低，LMCache offload 层未被触发，收益来自 KV 复用的 prefill 节省。

**F5 会话感知调度。** A（FCFS）/B（priority-static）/C（准入控制）三组对照（KV pool 仅 1.27 GiB 制压，6 并发）。A≈B（KV 命中率 0.48 vs 0.46，P50 114s vs 109s），静态 priority 单独不增益。C 组实现 0 抢占、KV 命中率 0.93（+45-47pp）、P50 降至 90s（-21%）、eviction-hit-idle 100%（3/3 runs）。D 组叠加 SimpleCPUOffloadConnector 后 P50 进一步降至 47s（C 组的 1.9× 更快），QPS +16%。

**MCTS 多路径决策。** HotpotQA 30 题/组（A：无 cache N=2，B：N=1，C1：N=2，C2：N=4，C3：N=8）。C2 组成功率最高（53.3%）。KV 命中率随分支数从 B 组 73.3% 升至 C3 组 80.0%，定性地验证了 APC 隐式 CoW 在分支推理中的复用潜力。需注意引擎未在组间独立重启，KV 命中率存在累计假象，绝对值不可直接引用。


# 第 5 章　实现难点说明

**一、Ascend C8 KV 量化的三坑突破。** F1 在 Ascend 平台遭遇三个紧密关联的障碍。第一个是 FULL graph 死锁：C8 attention 路径在 FULL ACL-graph capture 下 decode 大 batch 确定性死锁（Qwen2 batch≥26，NPU 101W 空转），排查后改为 FULL_DECODE_ONLY（prefill FULL + decode eager）绕开。第二个是校准精度：初次校准从 pre-RoPE 的 `k_proj` 采 scale，但 KV Cache 存储的是 post-RoPE K。Qwen3 第 0 层 RoPE 将振幅放大 435×，pre-RoPE scale 偏小导致 68% 饱和截断→输出垃圾。改 monkeypatch `apply_rotary_pos_emb` 从 post-RoPE 采 scale 后误差降至 0.5%。第三个是跨架构注入：vllm-ascend 的 `patch_gqa_c8.py` 不覆盖 Qwen2 架构，利用 Python sitecustomize.py 机制（每个解释器启动必跑，含 EngineCore 子进程）实现自动注入。

**二、多版本环境隔离与依赖冲突。** vLLM 需要 transformers 5.x，LLMLingua 需要 transformers 4.x，两者无法共存。通过创建隔离 `.venv-compress` + `_SubprocessCompressorPool`（JSONL RPC 常驻子进程）解决，worker 内 BERT 模型懒加载一次跨请求复用。numpy 2.4.6 ABI 破坏→锁定 1.26.4。lmcache 0.5.1 CUDA 版→降级 0.4.4 + `NO_CUDA_EXT=1`。gpt2 默认 64 线程反而不如限 32 线程快——小模型上线程调度的开销超过并行收益。

**三、Agent 协议结构感知的上下文压缩。** 标准压缩算法不理解 OpenAI tool-calls 协议，可能裁掉 `call_id` 或破坏 `arguments` JSON → API 400 错误。解决方案是在压缩前做物理拆分：protected prefix（tool_calls 结构 + 关键字段白名单）完全不送压缩器，仅 compressible body 进入 LLMLingua-2。冷热切分边界前移至完整 assistant-tool group 确保不产生孤立 tool message。关键字段白名单覆盖 ID/金额/状态/时间/联系等 30+ 模式。

**四、结构化检索接口的正确性修复。** 首版 F3 仅支持行分页，18,658 token 的 minified JSON（全文一行）导致 head/middle/tail 检索 0/3。引入受限字段搜索（`match_field`/`match_value`/`match_mode`）后，模型自行生成选择器一次 fetch 完成定位→3/3。搜索语法限四种确定匹配模式，不支持正则/JSONPath/表达式。

**五、会话感知调度的关键发现。** 最初预期 priority scheduling 能显著改善调度，但实测 A≈B（静态 priority 不增益）。真正增益来自 KV-pool 准入控制：KV ~72% 时主动降并发→不溢出→0 抢占→KV 命中率 0.46→0.93。这促使设计重心从"优化驱逐选择"调整为"防止驱逐发生"。

**六、NPU 卸载路径的废弃识别。** 最初计划使用 `NPUOffloadingSpec` 路径，经源码分析发现该路径已被上游废弃（e2e 测试 `@pytest.mark.skip`、import drift、架构 drift），升级版本或 fork 均无法解决。转而使用 shipping 的 `SimpleCPUOffloadConnector`（注册时自动→`AscendSimpleCPUOffloadConnector`，NPU 原生），无需任何版本变更→D 组 P50 47s。


# 第 6 章　总结

本作品基于 vllm-ascend 推理框架和华为 Ascend 910B2C NPU 国产硬件平台，针对 LLM Agent 长生命周期推理的五大内存特征，设计并实现了覆盖五个技术方向的系统性内存优化方案。F1 int8 KV 量化在 Qwen2.5-7B 上实现 KV token 容量翻倍，并发 16 下吞吐提升 35%。F2 上下文压缩在 τ-bench 全量 115 任务中降低 Prompt 19.32%，成功率不降反升。F3 工具数据外置在合成长结果中降低 Prompt 92.98%，在 2Wiki 100 题中累计降低 66.03% 且正确率持平，消除 context overflow 失败。F4 分层存储实现延迟降低 21%、吞吐提升 32%。F5 会话感知调度实现零抢占、KV 命中率跃升 45-47pp 至 0.93、P50 延迟最低降至 47 秒。系统配套构建了完整的 Benchmark Harness、20 个独立配置预设和 Gradio 实时展示前端。全部实验数据在国产平台上实测获得。
