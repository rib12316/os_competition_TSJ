# 推理引擎层优化方案：KV Cache 量化与分层存储

## 摘要

推理引擎层是智能体内存管理系统五层架构中的第二层，位于国产化部署层之上、Agent 推理层之下，负责将模型推理过程中产生的 KV Cache 数据在显存中进行高效管理。本层包含两个正交的优化模块：F1 KV Cache 量化从精度维度降低每个 token 的存储开销，将 BF16 格式压缩至 int8，使同等显存下的 token 容量翻倍；F4 分层存储从位置维度将冷数据从昂贵的 HBM 迁移至 CPU 和磁盘，突破单一 HBM 的容量上限。两个模块均通过 vLLM 引擎的配置参数接入，不修改引擎源码，不改动 Agent 推理逻辑，对上层完全透明。本文从学术原理、工程实现、工作流程和模块协同四个角度对推理引擎层的优化方案进行系统阐述。

---

## 一、问题背景：Agent 推理对 KV Cache 的双重压力

在 Transformer 自回归推理过程中，每生成一个 token，其 Key 和 Value 激活值被缓存于显存中以供后续 token 的注意力计算复用。KV Cache 的显存占用可由下式表示：

\[
M_{KV} = 2 \times L \times H_{kv} \times d_h \times S \times B_{dtype}
\]

其中 L 为 Transformer 层数，H_kv 为 KV 头数，d_h 为每头维度，S 为序列长度，B_{dtype} 为数据类型的字节数。以 Qwen2.5-7B 为例（L=28，H_kv=4，d_h=128，BF16），每个 token 产生约 56 KiB 的 KV Cache。序列长度达到 32,768 时，单 session 的 KV Cache 约占 4.7 GB。在智能体多 session 并发场景中，多个会话的 KV Cache 同时竞争有限的 HBM 容量（Ascend 910B2C 单卡 64 GB，其中模型权重占约 14 GB，剩余约 50 GB 可供 KV pool 分配），显存压力显著。

Agent 推理场景进一步放大了这一压力：多轮对话使单 session 上下文持续累积，session 寿命远超 single-shot 请求，KV Cache 不会在短期内释放。同时，不同 session 的活跃度存在差异——部分 session 正密集交互，其 KV block 需要频繁访问；另一些 session 处于闲置状态，其累积的 KV 数据仍占用显存却不被使用。这形成了两个维度的优化需求：**降低每 token 的存储成本**（精度维度，F1）与**将闲置数据迁出昂贵存储**（位置维度，F4）。

## 二、F1 KV Cache 量化：精度维度的存储压缩

### 2.1 作用对象与目标

F1 的作用对象是存储在 HBM 中的 Key 和 Value 张量。这些张量在 vLLM PagedAttention 的 block 机制中以固定粒度（每 block 16 token）管理，每个 block 内包含该 block 对应 token 在所有层、所有 KV 头上的完整 K 和 V 数据。F1 的目标是将每个 KV block 中存储的浮点值从 BF16（每值 2 字节）压缩至 int8（每值 1 字节），使相同显存预算下 KV pool 可容纳的 token 数量翻倍。

### 2.2 量化方案与数学基础

F1 采用对称 per-channel int8 量化方案。对 KV Cache 中的 Key 和 Value 张量，沿每头维度 d_h 逐通道计算独立的 scale 因子：

\[
s_c = \frac{\max(|x_c|)}{127}, \quad q_c = \text{round}\left(\frac{x_c}{s_c}\right), \quad \hat{x}_c = q_c \cdot s_c
\]

其中下标 c 表示通道索引，x_c 为该通道的原始 BF16 值，s_c 为 scale 因子，q_c ∈ [-128, 127] 为量化后的 int8 值，x̂_c 为反量化恢复的近似值。对称量化不使用零点偏移，反量化仅需一次乘法。以 Qwen2.5-7B 为例（d_h=128，4 个 KV heads），每层共 512 个通道，每个通道有独立的 scale。per-channel 粒度相比 per-tensor 能更好地适应不同通道的数值分布差异，标准分布假设下的往返误差约 0.5%。

### 2.3 Ascend NPU 上的 C8 激活机制

在 Ascend NPU 上，int8 KV 量化被称为 C8（CANN int8）。其激活不依赖常规的 `--kv-cache-dtype int8` 参数（该参数在 vllm-ascend 0.22.1rc1 为空操作——后端 `attention_v1.py:1309` 硬断言 `scales==1.0`，全仓无 int8→C8 路由），而是通过两条路径协同触发：

**模型标注路径。** 向模型目录写入 `quant_model_description.json`，对所有权重文件中的所有 `.weight` 参数标记为 `"FLOAT"`（普通浮点精度），对每层 `k_proj.kv_cache_scale` 和 `v_proj.kv_cache_scale` 标记为 `"C8"`，并声明全局 `kv_cache_type: "C8"`。该文件在引擎加载模型时被解析，触发 `AscendC8KVCacheAttentionMethod`——vllm-ascend 的 C8 attention 方法——将注意力计算路由至 int8 路径。

**引擎参数路径。** 引擎启动时添加 `--quantization ascend`，通知 vLLM 启用 Ascend 量化子系统。该参数由 `f1-bench-c8.yaml` 配置中的 `c8.enabled: true` 驱动，`vllm_server.py` 的 `build_serve_args()` 自动将其翻译为 CLI 参数，同时注入 `--compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'` 以绕开 C8 在 FULL graph capture 下的 decode 死锁。

### 2.4 校准流程：post-RoPE 自校准

C8 是静态 per-channel 量化，scale 因子需在推理前确定并预先写入模型权重。校准的核心挑战在于确认 KV Cache 中实际存储的张量位置。通过 `scripts/verify_c8_rope.py` 诊断工具实测验证，vLLM V1 存入 KV Cache 的是**旋转位置编码应用后（post-RoPE）的 K 张量**，而非 `k_proj` 输出（pre-RoPE）。RoPE 旋转会显著改变 K 的逐通道振幅分布——Qwen3-0.6B 实测显示，第 0 层 post-RoPE K 的最大绝对值是 pre-RoPE 的 435 倍，第 7 层约为 29 倍，至第 27 层才接近 1.2 倍。若从 pre-RoPE 采 scale，早期层 scale 将偏小数个数量级，导致量化饱和截断（第 0 层 68% 的值超出 int8 表示范围）和输出乱码。

自校准脚本 `calibrate_c8_qwen2.py` 的流程：加载 Qwen2.5-7B 至 NPU；monkeypatch `transformers.models.qwen2.modeling_qwen2.apply_rotary_pos_emb` 在旋转后捕获 K 的逐通道 maxabs，同时从 `v_proj` 输出直采 V（V 无 RoPE）；运行 32 条覆盖零售、常识、推理等多领域文本的校准样本；对每层每通道计算 scale = max(|x|) / 127（钳制最小值 1e-8）；将 scale 注入模型 safetensors 文件（`kv_cache_scales.safetensors`）并更新分片索引（`model.safetensors.index.json`）。

### 2.5 图编译适配：FULL_DECODE_ONLY

C8 的 attention 计算走 `npu_fused_infer_attention_score` 配合 int8 分页 KV 和 per-channel antiquant，KV 数据按 NZ BNSD 布局存储。该路径在 FULL graph capture 模式下对 decode 阶段存在确定性死锁——Qwen2 模型 decode batch 达到 26 时 NPU 进入 101W 空转状态且永不完成。经排查确认死锁仅发生在 decode 阶段走 FULL graph 时，PIECEWISE 模式全程通过。解决方案是将编译模式设置为 `FULL_DECODE_ONLY`：prefill 阶段保持 FULL graph 以利用其矩阵乘优化，decode 阶段退化到 eager 模式绕开 graph capture。decode 每次仅处理增量 token（单个新 token 的注意力），计算量远小于 prefill，eager 执行的开销在 int8 KV 带宽收益的抵消下不再显著。

### 2.6 跨架构注入：sitecustomize 子进程补丁

vllm-ascend 官方的 `patch_gqa_c8.py` 仅覆盖 Qwen3、Glm4Moe 和 MiniMaxM2 三种架构的 GQA C8 适配，不覆盖 Qwen2。Qwen2.5-7B 属于 Qwen2 架构，其 C8 scale 加载需要额外的权重加载拦截逻辑。由于 vLLM V1 的 EngineCore 在**独立子进程**中加载模型权重，父进程（API server）中的 monkeypatch 不会传播到子进程。解决方案是利用 Python 的 `sitecustomize.py` 机制——该文件在每个 Python 解释器启动时自动执行（含 spawn 出的子进程），且环境变量和 PYTHONPATH 被子进程继承。`c8patch/sitecustomize.py` 通过 `QWEN2_C8_PATCH=1` 环境变量门控，在 EngineCore 子进程启动时自动将 `Qwen2ForCausalLM.load_weights` 包装一层 C8 scale 加载拦截器，使 scale 能被正确读取并注册到 attention backend。该补丁由 `vllm_server.py` 的 `engine_env()` 自动设置环境变量和 PYTHONPATH。

## 三、F4 分层存储：位置维度的冷热管理

### 3.1 作用对象与目标

F4 的作用对象是 KV Cache 的物理存储位置。在默认的 vLLM 部署中，所有 KV block 全量存放于 HBM 中。F4 的目标是将不活跃的 KV block 从昂贵且容量有限的 HBM 迁移至成本更低、容量更大的 CPU 主存和磁盘，为活跃数据腾出 HBM 空间，在有限显存下扩展系统的并发承载能力。

### 3.2 三级存储架构与数据迁移策略

F4 构建了 HBM→CPU→Disk 三级存储层次。第一级 HBM 存放当前活跃请求的 KV block，访问延迟约 1 微秒，容量 64 GB（含模型权重）。第二级 CPU 主存放置近期可能复用的 KV block，通过 PCIe/NPU 互联总线访问，延迟约 10 微秒，容量数百 GB。第三级磁盘存放长期不活跃的 KV block，访问需经文件 I/O 栈，延迟毫秒级，容量近乎无限。

迁移决策基于 KV block 的热度——最近访问时间和访问频率。核心机制包括三个层次。存储层：每个 KV block 写入 HBM 时，根据配置决定是否在 CPU 侧保留副本。在 `lazy_offload` 模式下，block 并不立即拷贝，而是在即将被 LRU 淘汰时才异步复制到 CPU，避免对仍活跃的 block 产生不必要的传输开销。查找层：新请求到来时，先查 HBM，未命中则查 CPU 层，仍未命中则查磁盘层——任何一层命中都可免于从头 prefill 重算。恢复层：命中的 block 从 CPU 或磁盘通过 `aclrtMemcpyBatchAsync`（Ascend 的异步内存拷贝 API）加载回 HBM，拷贝操作放入独立的 `torch.npu.Stream` 不阻塞当前推理计算流。

成本分析：单 block（16 token × 4 KV heads × 128 dim × 28 layers × 2 bytes ≈ 460 KB in BF16）的 PCIe 传输延迟约 10-20 微秒。该 block 的 prefill 重算需要完整的前向注意力计算通过全部 28 层 Transformer，即使经过算子优化，重算延迟也在数十毫秒量级。CPU 回读的成本约为重算成本的千分之一，这正是分层存储在命中时可免于重算的根本原因。

### 3.3 LMCache-Ascend 的集成与适配

LMCache 是实现三层 KV 分层存储的开源方案，LMCache-Ascend 是其在 Ascend NPU 上的社区适配版本。核心组件 `LMCacheAscendConnector` 已在 vllm-ascend 0.22.1rc1 的 `KVConnectorFactory` 中注册，在引擎启动时通过插件机制自动加载。本项目的集成工作聚焦于三方面：

**配置封装。** `f4-lmcache.yaml` 将 LMCache 参数封装为声明式配置：`connector: LMCacheAscendConnector` 指定使用 Ascend LMCache 插件，`role: kv_both` 表示同时作为 KV block 的生产者和消费者。`vllm_server.py` 中的 `render_kv_transfer_arg()` 函数将声明式配置翻译为 vLLM V1 的 flat JSON schema——`--kv-transfer-config '{"kv_connector":"LMCacheAscendConnector","kv_role":"kv_both"}'`。

**环境适配。** Ascend 910B2C 需设置 `SOC_VERSION=Ascend910B2C` 环境变量以正确编译 NPU 算子。当前环境的 lmcache 0.5.1 为 CUDA 编译版本，在 Ascend 上不可用，需降级至 0.4.4 并以 `NO_CUDA_EXT=1` 禁用 CUDA 扩展编译。`kv/lmcache_check.py` 提供 `check_lmcache_ascend()` 运行时可用性探测。

**降级兜底。** 备选方案为 vLLM 原生的 CPU offload——`kv_offload.yaml` 通过 `--kv-offloading-size 8` 和 `--kv-offloading-backend native` 两个参数提供仅 HBM↔CPU 的轻量级卸载方案。

### 3.4 KV Connector 框架的统一接入

F4 和 F5 Phase 2 共用 vLLM V1 的 KV connector 框架作为接入点。`kv/connector.py` 定义了 `KVConnectorConfig` 数据类和 `render_kv_connector_args()` 渲染函数，统一管理两个 connector 的配置翻译：`LMCacheAscendConnector`（F4，NPU↔CPU↔Disk 三级分层）和 `SimpleCPUOffloadConnector`（F5 Phase 2 复用，仅 HBM↔CPU 两级，注册时被 vllm-ascend 自动替换为 Ascend 原生实现）。该模块修正了三个关键 bug：connector 名从已废弃的 `pykvconnector` 修正为当前有效名称；去除了不被 vLLM 0.22.1 CLI 接受的 `--kv-connector` flag；JSON 格式从旧版嵌套结构改为 V1 flat schema。

## 四、两模块的协同关系与工作流程

### 4.1 正交性

F1（精度维）和 F4（位置维）在作用目标上是完全正交的。F1 降低的是"每 token 存储多少字节"——同一 block 内，BF16 下每 token 占 56 KiB，int8 下占 28 KiB。F4 改变的是"哪些 block 存在哪里"——热 block 留在 HBM，温 block 搬到 CPU，冷 block 落到磁盘。两者可以独立启用或同时启用：单独开启 F1，所有 block 仍在 HBM 但每个 block 体积减半；单独开启 F4，block 体积不变但不活跃的会被迁移到更低层级的存储；同时开启，block 体积减半且不活跃的会被迁移——两个维度的收益叠加。

### 4.2 在推理流程中的介入点

一次 Agent 推理请求经过推理引擎层的完整路径如下。请求到达后，vLLM Scheduler 首先通过 APC 进行前缀匹配：将请求 token 序列按 block 粒度计算哈希值在全局哈希表中查找匹配 block——若命中（如 system prompt 和 tools schema 完全匹配），直接复用对应 block 的 KV 数据，免去 prefill 计算；若未命中，分配新 block 并进行 prefill 计算。

新产生的 KV block 在写入 HBM 前经过 F1 处理：若 C8 已启用，prefill 产生的 K 和 V 张量在存入 block 前被量化为 int8 格式——利用预先校准好的 per-channel scale 将 BF16 值映射为 int8 值存储，预填充阶段不增加可见延迟。后续 decode 阶段生成新 token 时，新产生的 K 和 V 同样经 C8 量化后追加到对应 block。

当新请求需要进行注意力计算时，F1 进行反量化：从 KV block 中读取 int8 权重，乘以对应通道的 scale 恢复为 BF16 近似值，参与标准的注意力计算——反量化仅需一次乘法，开销可忽略。同时 F4 在 block 生命周期中并行运作：查找阶段，若请求的 block 不在 HBM 中，LMCache 逐层向下查找 CPU 副本和 Disk 副本，命中则异步加载回 HBM；存储阶段，block 写入 HBM 后若 `lazy_offload` 开启，不立即拷贝至 CPU，等待 LRU 淘汰信号；释放阶段，block 被 LRU 选中淘汰时，F4 在释放前通过异步拷贝在 CPU 保留副本，为后续命中提供 second-chance 机会。

### 4.3 配置驱动的一键激活

两个模块均通过配置驱动方式接入引擎。F1 的 `f1-bench-c8.yaml` 中 `c8.enabled: true` 触发 `--quantization ascend` 和 `FULL_DECODE_ONLY` 编译模式，`c8.patch_qwen2: true` 触发 sitecustomize 子进程补丁注入。F4 的 `f4-lmcache.yaml` 中 `kv_transfer.connector: LMCacheAscendConnector` 触发 `--kv-transfer-config` JSON 参数。两者在配置层面互不影响，可独立开关或自由组合。F1 的模型标注和校准在引擎启动前完成，F4 的连接器在引擎启动时自动注册，两者对上层 Agent 逻辑完全透明——Agent 代码无需任何修改即可受益于引擎层的双重优化。

## 五、实测效果

### 5.1 F1 KV 量化

在 Qwen2.5-7B-Instruct 模型上，相同 41.5 GiB KV pool 预算下，C8 int8 的 token 容量为 1,556,992（BF16 baseline: 775,936），实现 2.007 倍容量提升。受控并发负载测试中，并发 16 时 C8 聚合吞吐 830.3 tok/s（baseline 616.5 tok/s，+35%），P95 尾延迟 2.58 秒（baseline 5.08 秒，-49%）。并发 32 时吞吐 1,443.2 tok/s（baseline 1,410.4 tok/s，+2.3%）。post-RoPE 自校准的往返误差控制在约 0.5%，常识和算术推理输出连贯正确。

### 5.2 F4 分层存储

在 τ-bench retail 评测中，单 Agent 10 任务场景下 LMCache 将 e2e P50 延迟从 152.8 秒降至 120.8 秒（降幅 21%），成功率从 0.20 提升至 0.40。并发 4 Agent 场景下 QPS 从 0.028 提升至 0.037（增幅 32%）。HBM 峰值在两项测试中均未明显变化——τ-bench 单任务 prompt 约 7,000 token，并发度低，KV pool 始终够用，LMCache 的 offload 层未被触发。当前结果中的收益主要来自 LMCache 的 KV 复用减少了 prefill 重算，offload 层的显存收益需在更长序列或更高并发的工作负载下验证。

## 六、总结

F1 KV Cache 量化和 F4 分层存储共同构成推理引擎层的两大优化支柱。F1 从精度维度将每 token 存储从 2 字节压缩至 1 字节，是确定性、无运行时开销的容量翻倍方案。F4 从位置维度将 KV block 在 HBM、CPU 和磁盘之间动态迁移，是在显存受限场景下突破容量上限的系统级方案。两者在数学上独立（精度维 vs 位置维）、在介入点上分离（写入前量化 vs 生命周期管理）、在工程上一致（均通过 vLLM 配置参数接入，不修改引擎源码，对 Agent 透明），可独立评测也可自由组合。当前 F1 已在 Qwen2.5-7B 上实现 2× KV 容量的端到端验证，F4 在 τ-bench 负载上验证了延迟和吞吐收益但仍需更长序列场景来展示 offload 层的显存效果。
